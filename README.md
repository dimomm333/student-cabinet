# Университетская информационная система

Публичный REST API расписания: `/api/v1/schedule`, `/api/v1/groups`, `/api/v1/teachers`. [Контракт, примеры интеграции и ограничения API](./docs/schedule-api.md). Только чтение; отдельный сервер не требуется. Проверка: `npm run test:api` после production build.

Прототип вымышленного Северного университета на Next.js **16.4.6**, TypeScript, React 19, Prisma **7.10.1** и SQLite. Одна база и общая авторизация Better Auth **1.7.22** обслуживают пять отдельных кабинетов. Все демонстрационные люди, учебные сведения и события вымышлены.

Публичная главная и новости доступны без входа. Кабинеты требуют сессию и соответствующую роль; меню само по себе не является защитой. Студенческий интерфейс сохранён, имя и профиль обучения теперь берутся из базы.

Кабинет деканата: [область доступа, работающие страницы, миграция и ограничения](./docs/deanery.md). Для безопасного обновления существующей SQLite: `npm run db:generate`, затем `npm run db:deanery` (согласованная копия, проверка на копии, миграция и добавление только нового демоаккаунта).

Управление расписанием: [регулярные пары, замены, отмены, конфликты и конкурсный сценарий](./docs/schedule-editor.md). Обновление существующей SQLite с явными демосвязями: `npm run db:generate`, затем `npm run db:schedule-editor`. Проверка редактора: `npm run test:schedule:editor` после production build.

Главная содержит две большие кнопки: личный кабинет и [публичное расписание](http://localhost:3000/schedule). Под ними — полезные объявления из базы с явной маркировкой вымышленных материалов. Расписание использует общие модели групп, дисциплин, преподавателей и занятий, поддерживает неделю/дни, поиск и числитель/знаменатель. [Архитектура, миграция и отчёт проверок](./docs/schedule.md).

## Запуск

Нужен Node.js 22.18+ в ветке 22, либо Node.js 24 или 26. Проверено на Node.js 26.13.0. В Windows PowerShell при запрете скриптов используйте `npm.cmd` вместо `npm`.

Из корня проекта:

```powershell
# Только если .env ещё нет. Существующий файл не заменяйте.
Copy-Item .env.example .env
npm.cmd ci
npm.cmd run auth:setup
npm.cmd run db:setup
npm.cmd run dev
```

`auth:setup` добавляет недостающие локальные настройки и случайный секрет в `.env`, сохраняя существующие значения. Скрипт не выводит секреты. Если все настройки переданы через окружение процесса, файл не требуется.

Откройте [главную](http://localhost:3000) или [общий вход](http://localhost:3000/login). В VS Code сохранена задача `Student cabinet: dev`.

Для существующей базы перед применением миграций сделайте резервную копию SQLite при остановленном приложении либо средствами SQLite Backup/VACUUM INTO. Затем выполните:

```bash
npm run db:generate
npm run db:deploy
npm run db:seed
npm run db:status
```

Миграции сохраняют прежние данные. `db:seed` добавляет отсутствующие демонстрационные записи и профили, инициализирует отсутствующие credentials, а также создаёт общее расписание. Только три известные демоновости обновляются по прежним ID: их тексты теперь посвящены льготам, корпусам и документам. Другие новости, пользователи, роли, пароли и сессии не очищаются. Сброс базы и `db push` не нужны. Уже применённые SQL-миграции не редактируйте.

## Окружение и данные

Безопасный пример — [.env.example](./.env.example). Реальные пароли и секреты в примере отсутствуют.

- `DATABASE_URL` — локальный SQLite-файл, по умолчанию `file:./prisma/dev.db`. Относительный путь считается от корня проекта. Приложение, Prisma CLI и seed используют общий преобразователь пути; не задавайте другой файл в `.env.local`.
- `BETTER_AUTH_URL` — точный origin приложения. Локально `http://localhost:3000`; для внешнего адреса требуется HTTPS. Входите через указанный hostname, чтобы проверка origin прошла.
- `BETTER_AUTH_SECRET` — случайный секрет не менее 32 символов. `auth:setup` генерирует 48 случайных байт. Для развёртывания задайте отдельный секрет в окружении сервера.
- `AUTH_TRUST_PROXY` — по умолчанию `false`: клиентские IP-заголовки игнорируются. Для внешнего адреса требуется `true` и доверенный proxy.
- `AUTH_PROXY_SECRET` — отдельный случайный секрет не менее 32 символов, общий только у proxy и приложения; нужен при `AUTH_TRUST_PROXY=true`. Подробности — в [настройках production](./docs/auth-security-fixes.md#reverse-proxy-и-firewall).

[Схема Prisma](./prisma/schema.prisma) содержит User, News, три профиля, служебные модели Better Auth и общую структуру расписания: StudyGroup, Discipline, Lesson, LessonGroup, LessonTeacher, AcademicTerm, ScheduleEntry, Building, Room. Связи и публичные поля описаны в [документации расписания](./docs/schedule.md). Таблицы оценок, услуг и технических заявок не создавались.

Публичные новости читаются из базы на каждый запрос: три последние опубликованные записи. Ошибка чтения и пустая база обрабатываются в интерфейсе. База, окружение, сгенерированный Prisma Client и локальные резервные копии исключены из Git через [.gitignore](./.gitignore).

## Архитектура авторизации

[src/lib/auth.ts](./src/lib/auth.ts) настраивает Better Auth с Prisma adapter. Пароли хешируются scrypt со случайной солью. Серверные hooks ограничивают сессии восемью часами от исходного createdAt независимо от rememberMe; при каждом чтении проверяется абсолютный срок, включая старые длинные сессии. Автопродление отключено, update hook не позволяет сдвинуть начало сессии. Cookie имеет HttpOnly, SameSite=Lax, а при HTTPS — Secure; cookie-cache отключён. Выход подтверждается только после проверки отсутствия Session в базе. При отказе удаления API возвращает 503 и сохраняет cookie для повторной попытки.

После развёртывания исправления старые записи сессий можно заранее ограничить командой `npm run auth:harden-sessions`. Пользователи, их пароли и новости этой командой не меняются. Старые сессии за пределами восьми часов недоступны сразу после обновления приложения, даже до выполнения команды.

[src/lib/access.ts](./src/lib/access.ts) читает серверную сессию и актуальную роль из базы. Каждая закрытая страница и её layout вызывают `requireRole`. Без сессии происходит redirect на `/login`; при несовпадении роли — в собственный кабинет. Администратор имеет отдельный кабинет; автоматического доступа к остальным ролям нет. При добавлении Route Handler или Server Action обязательно проверяйте сессию и права внутри самой операции, близко к данным.

Публичный auth API разрешает только `POST /api/auth/sign-in/email`, `POST /api/auth/sign-out` и `GET /api/auth/get-session`. Регистрация, изменение пользователя, привязка аккаунтов и управление ролями через API недоступны. Поле `role` также имеет `input: false` в конфигурации библиотеки. Logout выполняет полный переход к странице входа, очищая кеш навигации браузера.

Сохранены Cache Components и Partial Prefetching установленной Next.js. Чтение сессии находится под Suspense; личные данные не входят в статическую оболочку. React `cache()` используется только для устранения повторных запросов в рамках одного серверного рендера.

Ограничение входа — пять попыток за фиксированное окно 60 секунд на нормализованный email, независимо от IP и наличия пользователя. Ключ хранится как HMAC, счётчик изменяется атомарным параметризованным SQL. Отклонённые запросы не продлевают окно, постоянной блокировки аккаунта нет; успешный вход очищает своё окно. Дополнительный лимит Better Auth — 60 запросов входа в минуту на проверенный IP либо общую корзину локального прямого запуска. Клиентские X-Forwarded-For и подобные заголовки не используются. Подробные ограничения и защита от DoS описаны в [отчёте исправлений](./docs/auth-security-fixes.md). SQLite рассчитана на Node.js с постоянным локальным диском.

## Кабинеты и ограничения

- `/dashboard` — прежний дизайн студента: приветствие и профиль из базы; существующие демонстрационные занятия, показатели и уведомления остаются учебными примерами. Демонстрационная дата — 11 ноября 2026 года.
- `/teacher` — главная, расписание, дисциплины и группы, студенты, журнал оценок, материалы, консультации, объявления.
- `/staff` — главная, технические заявки, оборудование, аудитории, задачи, уведомления.
- `/admin` — главная, пользователи, новости, заявки студентов, учебные данные, настройки.

Новые кабинеты содержат работающую навигацию и явно обозначенные страницы будущих модулей. Управление пользователями, CRUD новостей, оценки, расписание, услуги, заявки, восстановление пароля, MFA и администрирование сессий пока не реализованы. Назначение роли выполняется только доверенными серверными/административными операциями с базой; пользовательского редактора роли нет.

## Проверки

```bash
npm run typecheck
npm run lint
npm run build
npm run test
npm run start
```

После сборки, с подготовленной демонстрационной базой:

```bash
npm run test:auth
```

[scripts/verify-auth.mjs](./scripts/verify-auth.mjs) запускает [изолированный набор тестов](./scripts/verify-auth-security.mjs): он сам делает копию SQLite, задаёт временные пароли только в копии и запускает сервер на localhost. Уже работающий сервер не нужен. Проверяются все шесть аккаунтов, пять ролей, вложенные маршруты и RSC, вход/выход, CSRF, лимит при смене IP, нормализация email, конкурентные попытки, восьмичасовой предел, legacy-сессии и искусственный отказ удаления при logout. Отдельная команда `npm run test:auth:dev` проверяет limiter в настоящем next dev на копии проекта. Основная база не меняется; результаты и закрытые тестовые копии находятся в игнорируемом локальном каталоге.

Подробный [отчёт об изменённых файлах и выполненных проверках](./docs/authentication.md).
