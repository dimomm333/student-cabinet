# Электронный обходной лист

Обходной лист подтверждает внутренние проверки подразделений при выпуске, подготовке к отчислению или переводе в другую образовательную организацию. Его открывает деканат по подтверждённому основанию. Заявление на отчисление остаётся отдельным процессом услуг. Создание и завершение обходного листа не меняют академический статус, пароль, группу или право входа пользователя и не создают приказ.

## Архитектура и модели

Единая реализация для всех кабинетов: [серверный репозиторий](../src/lib/clearance-repository.ts), [полномочия](../src/lib/clearance-permissions.ts), [валидация команд](../src/lib/clearance-shared.ts), [Route Handler](../src/app/api/clearance/route.ts), [общий интерфейс](../src/components/clearance-workspace.tsx), [настройки](../src/components/clearance-settings.tsx).

В [Prisma-схеме](../prisma/schema.prisma) добавлены 12 моделей:

| Модель | Назначение |
| --- | --- |
| ClearanceDepartment | Устойчивый ID, код, описание, контакты, активность, порядок и версия подразделения |
| ClearanceGrant | Явное назначение сотрудника на конкретное подразделение |
| ClearanceTemplate | Основание, название, активность и версия шаблона |
| ClearanceTemplateRule | Нормализованные правила применимости подразделений шаблона |
| ClearanceProcess | Студент, область деканата, основание, реквизиты, снимок шаблона/ФИО/группы, состояние и версия |
| ClearanceStep | Снимок конкретной проверки, её применимость и сохранённое решение сотрудника |
| ClearanceRemark | Подтверждённое замечание: категория, описание, действие студента, контакт, срок, сумма в копейках, устранение |
| ClearanceReply | Ответ студента либо результат повторного рассмотрения сотрудником |
| ClearanceHistory | Дописываемая история, снимки имени/ID исполнителя, серверное время и видимость студенту |
| ClearanceDocument | Неизменяемые PDF, SHA-256, итоговый снимок и отметка аннулирования |
| ClearanceReceipt | Ключ идемпотентности пользователя, хеш всей команды и результат |
| ClearanceWriteState | Сериализация серверных команд до чтения данных |

Внешние ключи защищают процессы от потери владельца, подразделения, связанного заявления и документов. ID и имена исполнителей дополнительно сохранены как исторические значения: переименование сотрудника не меняет прежнее решение. Удаление назначенного сотрудника ограничено связями; для прекращения доступа отзываются назначения и сессии. API бесследного удаления решений, замечаний, процессов или истории отсутствует.

Конфигурация копируется в шаги при создании черновика. Редактирование справочника и шаблона влияет на будущие процессы. Подготовленный черновик можно отменить и создать заново, если нужен другой шаблон. Необходимые дополнительные шаги добавляет деканат с обоснованием; шаг не удаляется, а может быть признан неприменимым с основанием. Согласованный пункт нельзя незаметно исключить. Открытое замечание не позволяет деканату исключить проверку.

История настроек содержит причину и значения до/после изменения подразделения, шаблона или назначения. Эти записи доступны администратору и не входят в студенческую историю. Поиск очередей и сотрудников разбивается на слова; для обычного русского написания ФИО и кодов групп проверяются исходный, нижний, верхний регистр и написание с прописной буквы средствами Prisma. Это учитывает ограничение SQLite LIKE без загрузки всех пользователей в память; произвольная нестандартная смесь регистров внутри сохранённого имени не нормализуется автоматически.

## Подразделения и правила

Команда `npm run clearance:configure` добавляет только отсутствующие базовые записи и шаблоны. Она не создаёт пользователей, обходные листы или долги и не перезаписывает существующую конфигурацию.

| Подразделение | Правило |
| --- | --- |
| Библиотека | ALWAYS: обязательная проверка |
| Бухгалтерия | ALWAYS |
| Выпускающая кафедра | ALWAYS |
| Бюро пропусков | ALWAYS |
| Общежитие | DORMITORY: известное проживание либо ручное уточнение |
| Договорной отдел | PAID: известное договорное обучение либо ручное уточнение |
| Лаборатория и материальная служба | EQUIPMENT: ручное уточнение, пока нет достоверного источника выдачи |
| Отдел практик | GRADUATION: требуется для выпуска; для других оснований сохраняется мотивированное «Не требуется» |
| Деканат | FINAL: отдельная итоговая проверка |

Администратор может создавать подразделения и шаблоны, менять контакты, активность и правила, назначать ответственных. Дополнительное правило MANUAL требует уточнения. В шаблоне должно быть от 2 до 30 уникальных подразделений и ровно одно FINAL. Воинские и миграционные проверки автоматически не назначаются.

Отсутствие сведений о проживании, оборудовании или договорных обязательствах не считается отсутствием долга. Неизвестные условия блокируют запуск до обоснованного решения деканата. Даже текущая отметка «не проживает» не доказывает отсутствие прежних обязательств общежития. Для известных договорных данных проверяется существующее поле fundingBasis; непонятные значения оставляются на ручное уточнение.

Перед открытием сервер также проверяет наличие действующих ответственных на необходимых обычных шагах. Деактивация подразделения блокирует новые подписи и делает назначение на него недействующим; ранее сохранённые решения не стираются.

## Роли и доступ

| Роль | Доступ |
| --- | --- |
| STUDENT | Только собственные открытые и исторические листы; ответ на незакрытое замечание; собственный завершённый PDF |
| TECHNICAL_STAFF | Только подразделения с активным ClearanceGrant; ФИО/группа и свои проверки/замечания/история; без основания отчисления, реквизитов приказа, чужих замечаний и общего PDF |
| DEANERY_STAFF | Только область действующих DeaneryDepartmentAssignment на AcademicDepartment процесса и текущей группы студента; подготовка, уточнения, запуск, напоминания, отмена и завершение |
| ADMIN | Настройка, наблюдение и журнал; отдельное подтверждённое аннулирование итогового документа с причиной; обычная подпись за подразделение запрещена |
| TEACHER | Доступа к модулю и права согласования нет |

Для обычной проверки сотруднику деканата дополнительно нужен ClearanceGrant на подразделение. Финальная проверка опирается на полномочия деканата. Назначение глобальной роли не предоставляет подпись за библиотеку, бухгалтерию или общежитие. Назначать STUDENT, TEACHER или ADMIN ответственным через команду модуля запрещено.

Полномочия, текущая роль и абсолютный срок сессии перечитываются у данных в каждой транзакции. Отзыв назначения закрывает карточку и старые уведомления. Layout не заменяет эти проверки. Страницы используют действующие requireRole, connection и Suspense/loading. Cache Components и Partial Prefetching сохранены; сессии и решения о доступе не кешируются между запросами. SEC-01/02/03 не ослаблялись.

## Состояния и согласования

```text
DRAFT → IN_PROGRESS ⇄ ACTION_REQUIRED
              ↓              ↓
        READY_FOR_FINAL_REVIEW
              ↓ решение деканата
          COMPLETED

Любое незавершённое состояние → CANCELLED (деканат, причина)
COMPLETED → CANCELLED (администратор, аннулирование, причина)
```

IN_PROGRESS, ACTION_REQUIRED и READY_FOR_FINAL_REVIEW вычисляются из действительных шагов. Число согласований, сводные счётчики и прогресс читаются из БД. Итоговый шаг и неприменимые проверки не входят в прогресс подразделений: 4 согласования из 5 необходимых не превращаются в 7 согласований за счёт трёх исключённых пунктов. Для обычного шага доступны PENDING, IN_REVIEW, ACTION_REQUIRED, APPROVED, NOT_APPLICABLE. Для NOT_APPLICABLE требуется основание.

Сотрудник начинает проверку, фиксирует подтверждённое замечание либо согласует. Замечание остаётся открытым после сообщения студента; responsePending означает ожидание повторного рассмотрения. Сотрудник возвращает ответ с объяснением или подтверждает устранение и согласует. Самостоятельно снять задолженность студент не может. Снятые замечания и все ответы сохраняются. Новое подтверждённое замечание может возобновить согласованный шаг до окончательного завершения и отозвать готовность к финальной проверке.

Финальное завершение повторно проверяет все обязательные шаги, применимость и отсутствие незакрытых замечаний в той же транзакции, которая сохраняет подпись деканата и документ. После завершения обычные изменения запрещены. Аннулирование не переписывает PDF и прежние решения: документ получает invalidatedAt, процесс — CANCELLED, скачивание блокируется, причина видна в истории и участникам приходит уведомление.

Уникальный nullable activeKey резервирует сочетание «студент + основание» и для черновика. При отмене/завершении резерв освобождается; история остаётся. Другие основания могут существовать независимо.

Все команды сначала получают write lock обновлением ClearanceWriteState, затем проверяют сессию, права и версию. Повтор одинаковой команды возвращает сохранённый результат; изменённая команда с тем же ключом отклоняется. Хеш включает вложенные правила шаблона. Запрос с устаревшей версией получает 409. Отклонённый конфликт версии отдельно фиксируется во внутреннем журнале и адресно сообщает деканату о необходимости проверки, без содержимого отклонённого запроса.

## Кабинеты и API

Маршруты: `/dashboard/clearance`, `/staff/clearance`, `/deanery/clearance`, `/admin/clearance`. Новый раздел добавлен в меню и на рабочие столы сотрудников. Студенту показываются собственный активный процесс, замечания и архив; при отсутствии процесса — «Обходной лист не требуется». История свёрнута. Формы опасных решений используют доступные с клавиатуры нативные диалоги, обоснование и подтверждение. Текст выводится обычным React-рендером, без HTML-вставок.

Закрытый API `/api/clearance`:

| Запрос | Результат |
| --- | --- |
| GET view=list&page=0&q=…&group=…&status=…&reason=…&departmentId=… | Разрешённая очередь, 20 записей, total и реальные счётчики; фильтр reason запрещён персоналу подразделений |
| GET view=detail&id=…&page=0 | Разрешённые сведения, шаги, замечания и 30 событий истории |
| GET view=context&q=…&page=0 | Доступные справочники; поиск студентов деканата или сотрудников для настройки, по 20 результатов |
| GET view=pdf&id=… | Только разрешённый, неаннулированный завершённый PDF |
| POST application/json | CREATE, OPEN, START, REMARK, REPLY, REJECT_REPLY, APPROVE, APPLICABILITY, ADD_STEP, REMIND, CANCEL, COMPLETE, INVALIDATE, DEPARTMENT, TEMPLATE, GRANT |

Общие поля команд: operation, requestId (16–100 допустимых символов), id и version для изменений существующего процесса/настройки. Клиент не передаёт итоговый статус, подписавшего или время решения. Неизвестные и защищённые поля отклоняются. POST проверяет точный Origin из BETTER_AUTH_URL и Sec-Fetch-Site; JSON ограничен 32 КиБ и 15 секундами приёма. Ответы, включая ошибки и PDF: `private, no-store`, `Vary: Cookie`, `nosniff`. PDF — attachment с CSP sandbox. Анонимный доступ — 401, неправильные полномочия — 403/404, конфликт — 409, некорректное тело — 400/413/415, техническая ошибка — 503 без приватных деталей.

В истории применяется серверная пагинация. У карточки ограничены последние 30 замечаний каждого шага и последние 10 ответов каждого замечания; полная лента действий сохраняется и доступна постранично. Одновременно открытых замечаний на шаг — не более 20. Конфигурационные списки ограничены 200 подразделениями и 100 шаблонами. Напоминание разрешено не чаще раза в час на процедуру.

## Уведомления и интеграции

Используются существующие NotificationEvent, Notification, настройки, счётчики и email outbox; отдельной системы доставки нет. Источник CLEARANCE связан внешним ключом с процессом, категория SERVICES. События и адресные уведомления коммитятся вместе с решением. SourceKey содержит ID/версию/тип; receipt защищает повтор действия. Уведомления о конфликтах отдельно идемпотентны по ключу запроса.

События: открытие, замечание, ответ студента, повторное устранение, согласование, снятие замечания, готовность к финальной проверке, завершение, отмена/аннулирование, дополнительная проверка, уточнение и напоминание. Новые проверки и ответы направляются действующим ответственным; деканат получает готовность и конфликты. Уведомления содержат нейтральный текст и конкретную защищённую ссылку, без долгов и причины отчисления. Чтение inbox и email worker повторно применяют clearanceScope; отзыв прав закрывает доставку. Письма обходного листа имеют соответствующую тему и нейтральный текст, без копирования замечаний.

Связь с услугами — необязательный serviceRequestId на существующее принятое заявление withdrawal. Создание требует того же владельца, состояния IN_REVIEW/IN_PROGRESS/COMPLETED и действующей области serviceProcessorScope сотрудника. Черновик или отправка заявления не открывают обходной автоматически. Вложения и статусы услуг не дублируются.

Для открытого шага «Общежитие» студент и действующий проверяющий видят подтверждённое проживание, состояние выезда, возврат ключей и имущества и наличие остатка к оплате. Назначенный сотрудник принимает решение вручную. Ранее завершённые шаги и их документы сохраняются. [Интеграция общежития](./dormitory.md)

Ответ студента сейчас текстовый. Загрузка подтверждающего файла в этой версии не добавлялась: она необязательна для рабочего сценария. Общая файловая инфраструктура услуг остаётся прежней; публичных каталогов документов модуль не создаёт.

## Итоговый PDF

[Генератор](../src/lib/clearance-pdf.ts) использует уже установленные sharp и pdf-lib. PDF создаётся из сохранённых серверных решений, содержит университет, уникальный номер, ФИО, группу, основание, даты, все решения подразделений и итогового сотрудника. Имена исполнителей и состав проверок — снимки. PDF и снимок сохраняются один раз в ClearanceDocument; при скачивании проверяются право, состояние, invalidatedAt и SHA-256. Закрытая бинарная модель следует применяемому в проекте хранению официальных изображений в БД; отдельного публичного или внешнего файлового сервиса нет.

Страницы представлены растровыми изображениями 216 dpi с кириллицей: подходят для печати, но текст нельзя выделить или полноценно читать программой экранного доступа. Для Linux нужен системный шрифт с кириллицей, например пакет `fonts-dejavu-core`, и штатные зависимости sharp. Для доступного поискового PDF дальнейшее расширение — встраивание лицензированного шрифта в векторный документ. Подписи/печати не рисуются; документ имеет маркировку «Образец» и пояснение, что КЭП не применяется.

## Доступ при подготовке к отчислению

Конкурсный студент остаётся STUDYING; «начата подготовка к отчислению» хранится в основании процедуры и не имитирует изданный приказ. Учётная запись не удаляется. Модуль доступен существующей роли STUDENT и не требует «активного обучения» для собственного листа/PDF, поэтому сам по себе перевод академического статуса не уничтожает документы.

Глобальная политика ограниченного кабинета бывшего студента не вводилась в рамках этого модуля. Остальные образовательные API существующего ЛКС сейчас определяют доступ по роли и своим назначениям. Перед эксплуатацией для фактически отчисленных студентов необходимо отдельно согласовать и внедрить общую политику закрытия образовательных сервисов с сохранением только обходного листа, документов, необходимых уведомлений и выхода. Нельзя оставлять полный образовательный доступ только ради обходного листа; демосценарий не является реализацией такой политики.

## Миграция, резервирование и Linux

[Миграция](../prisma/migrations/20261120120000_clearance/migration.sql) создаёт новые таблицы, индексы и внешние ключи. В NotificationEvent добавляется nullable clearanceProcessId через ALTER TABLE без пересоздания старой таблицы. Старые события, пользователи, пароли, расписание, БРС, услуги и сессии сохраняются. Бизнес-слой использует Prisma API; activeKey и транзакционная блокировка не требуют SQLite partial index. При переходе на PostgreSQL потребуется сгенерировать соответствующую миграцию: SQL текущего файла и backup workflow предназначены для SQLite.

Команды выполняются последовательно:

```sh
npm ci
npm run db:generate
node --env-file-if-exists=.env scripts/prepare-clearance.mjs
npm run db:clearance
npm run clearance:configure
npm run build
```

Первая подготовка без --apply делает согласованную VACUUM INTO копию, пробует migrate deploy на второй копии, сравнивает каждое прежнее поле/число записей, проверяет integrity_check/foreign_key_check и повторное применение. `db:clearance` повторяет эти проверки и только затем применяет миграцию к исходной БД. Перед --apply следует остановить запись приложения: скрипт проверяет неизменность источника после резервирования, но обслуживание активной production-БД требует окна обслуживания. Файлы backup/report находятся в закрытом игнорируемом каталоге `.local/clearance-migration-*` и не должны публиковаться. Восстановление копии проверяется регрессией на изолированной БД; рабочую БД ради теста восстановления не заменяют.

На Linux выполняются новая установка по lock-файлу и сборка на целевой системе. Windows node_modules и сборочные артефакты не переносятся. Пути в переносимом коде строятся средствами Node.js. Данные SQLite и резервные копии требуют защищённого тома и отдельной операционной политики хранения.

## Подготовка демонстрации

[Сценарий заполнения](../scripts/seed-clearance.mjs) запускается только явным действием оператора. Автоматические тесты вызывают его общий fixture только на новой изолированной БД. В NODE_ENV=production демозаполнение запрещено. Существующие пользователи и их пароли не перезаписываются; конфликт идентичности или роли останавливает сценарий. Повторный запуск не создаёт второй процесс и не сбрасывает достигнутое состояние. Для повторной чистой демонстрации используйте новую изолированную БД.

Пароли не выводятся и не записываются сценарием в файлы. Права предоставляются только синтетическим аккаунтам. Seed создаёт синтетический профиль, отдельную область деканата и лист WITHDRAWAL. Бухгалтерия, кафедра, пропуска и общежитие уже согласованы назначенными сотрудниками через общую бизнес-логику; договор и оборудование обоснованно исключены деканатом по синтетическим данным; библиотека зарегистрировала возврат книги. Номера несуществующего приказа нет.

Существующий ADMIN используется для настройки, новый администратор не создаётся. Договорной отдел, лаборатория и отдел практик есть в справочнике, но отдельные демосотрудники им не создаются: если проверка будет необходима в другом сценарии, назначьте ответственных через администратора. Отсутствие назначения блокирует запуск.

## Краткий конкурсный сценарий

1. Войти синтетическим студентом; открыть «Обходной лист», показать основание, реальный прогресс и замечание библиотеки.
2. Нажать «Сообщить об устранении», описать возврат книги. Статус меняется на ожидание повторной проверки, долг остаётся открытым.
3. В другом профиле браузера войти сотрудником библиотеки; открыть назначенную проверку. Сотрудник видит только свой этап. При необходимости вернуть сообщение на уточнение.
4. После проверки нажать «Согласовать», указать результат. Замечание снимается, деканат получает готовность к завершению.
5. Войти сотрудником деканата; открыть конкретный лист и выполнить итоговую проверку через подтверждение.
6. Вернуться к студенту, открыть завершённый лист и скачать PDF. Показать историю. В архиве остаются предыдущие процедуры.
7. При необходимости показать настройки подразделений и ответственных в ADMIN. Администратор не может поставить подписи за всех.
