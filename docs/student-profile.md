# Университетский профиль студента

Страница `/dashboard/profile` доступна только студенту и показывает его собственные данные. Шапка содержит фотографию либо инициалы, ФИО, группу и статус обучения. Ниже расположены блоки личных данных, обучения, документов, общежития и учётной записи. Интерфейс доступен только для просмотра. Данные других ролей не переработаны.

## Данные и источники

В [StudentProfile](../prisma/schema.prisma) добавлены nullable-поля:

| Назначение | Поля |
| --- | --- |
| Личные данные | `lastName`, `firstName`, `middleName`, `gender`, `citizenship`, `contactPhone` |
| Обучение | `educationLevel`, `fundingBasis`, `enrolledAt`, `expectedGraduationYear`, `educationStatus` |
| Документы | `personalFileNumber` |
| Общежитие | `residenceStatus`, `dormitory`, `dormitoryRoom` |

Перечисление `EducationStatus`: `STUDYING`, `ACADEMIC_LEAVE`, `EXPELLED`, `GRADUATED`, `TRANSFERRED`. Восстановление не является постоянным статусом. Неизвестный статус — `null`, отображается «Не указано». `ResidenceStatus`: `RESIDENT` / `NON_RESIDENT`; `null` означает «Нет данных». При неизвестном статусе и непроживании название общежития и комната не выдаются за действительные сведения.

`StudentEnrollment` в существующей схеме отсутствует; новая дублирующая модель зачисления не создавалась. Группа, программа и курс берутся из связанной `StudyGroup`, институт — из её `AcademicDepartment.faculty`. Старые поля профиля используются как совместимый резерв при отсутствии соответствующей связи. Университетская почта и регистрация остаются в `User`. `User.name` используется в шапке, пока официальные фамилия и имя не заполнены; строка имени аккаунта не разбивается догадками. Прежний `studentNumber` сохранён в БД, но не отображается. Подтверждение почты из студенческого интерфейса убрано, Better Auth не изменён.

## Официальная фотография

[StudentOfficialPhoto](../prisma/schema.prisma) связан с `StudentProfile` один к одному по `userId`: `content Bytes`, `mimeType`, `updatedAt`. Фотография хранится в БД, за пределами `public/`, отдельно от Better Auth `User.image`. Путей хранения нет ни в ответах, ни в конфигурации приложения.

`GET /api/student/profile/photo` каждый раз проверяет текущую сессию и роль. В запросе к Prisma владелец определяется исключительно из сессии с повторным ограничением по роли. Нет параметра выбора владельца; любые query-параметры отклоняются. Анонимный запрос получает 401, другие роли — 403, отсутствующая фотография — 404. Другой студент получает только собственное изображение. Ответы имеют `private, no-store`, `Vary: Cookie`, `nosniff`, `Cross-Origin-Resource-Policy: same-origin`. Изображение загружается непосредственно из защищённого маршрута, без публичного оптимизатора Next Image. Методы загрузки отсутствуют.

[Обработчик фото](../src/lib/student-photo.ts) принимает JPEG, PNG и WebP до 5 МиБ и 16 миллионов пикселей, сверяет фактический формат с MIME, полностью декодирует изображение, отклоняет повреждённые и анимированные файлы. Затем нормализует ориентацию, уменьшает изображение до 1200×1600, перекодирует в JPEG и удаляет исходные EXIF/GPS и прочие метаданные. `sharp` уже использовался Next.js; теперь это явно закреплённая прямая зависимость с lock-файлом.

Для доверенного оператора с доступом к серверу и БД есть команда:

```sh
npm run db:student-photo -- <userId> <photo.jpg>
```

Это административная операция вне веб-интерфейса. Перед чтением проверяется размер файла, перед записью — существование студенческого профиля и актуальная роль. Публичного endpoint загрузки, редактирования деканатом и прав доступа сотрудников к новым персональным полям не добавлено. Будущий университетский процесс обязан отдельно проверять полномочия и назначения сотрудника перед использованием обработчика.

## Read-only и услуги

Студент не может менять официальные поля, фотографию или проживание. Существующий список разрешённых auth-маршрутов продолжает блокировать обновление пользователя. Блок «Нашли ошибку в данных?» ведёт в `/dashboard/services`. На профиле и в услугах прямо написано: «Изменение данных в ЛКС» пока недоступно, будущая заявка потребует проверки деканата. Формы отправки и фиктивного успешного результата нет.

## Миграция и демонстрационные аккаунты

[Миграция](../prisma/migrations/20261114120000_student_profile/migration.sql) только добавляет nullable-колонки и таблицу фотографий; старые записи не пересоздаются. [Подготовка БД](../scripts/prepare-student-profile.mjs) делает согласованный `VACUUM INTO`, мигрирует отдельную копию, проверяет все прежние поля всех таблиц, количество строк, внешние ключи, целостность и идемпотентность фото-seed. Перед применением проверяет отсутствие конкурентных изменений основной БД. После применения снова сверяет прежние данные.

Выполнено с сохранением всех прежних аккаунтов, ролей, сессий, групп, занятий и назначений. Резервная копия находится в игнорируемом каталоге `.local/student-profile-migration-WWpMgU/before.db`; файл не включается в Git.

Для двух явно известных демостудентов добавлены оригинальные геометрические иллюстрации с надписью «ДЕМО · ИЛЛЮСТРАЦИЯ». Реальные фотографии людей не использовались. Повторный фото-seed не меняет имеющееся изображение. Прочие неизвестные данные существующих аккаунтов не заполнялись. Общий seed также перестал дополнять отсутствующие официальные поля существующих студенческих профилей вымышленными значениями. Демо-значения создаются только для нового демоаккаунта.

```sh
npm run db:student-profile
node --env-file-if-exists=.env prisma/seed.ts --student-profile-demo-only
```

Реализация приложения использует Prisma; бинарные данные совместимы с PostgreSQL (`Bytes` → `bytea`). Текущие SQL-миграции, `VACUUM INTO` и скрипт резервного копирования предназначены для SQLite. При будущем переходе на PostgreSQL потребуется отдельная история миграций, адаптер и соответствующий механизм резервного копирования. Приложение не содержит абсолютных Windows-путей для фотографий.

## Два замечания предыдущего этапа

Старый тест расписания мигрировал и повторно заполнял копию рабочей БД, затем ожидал ровно 12 занятий. Добавленные пользователем записи сохранялись в копии и нарушали это предположение. Теперь копия нужна только для проверки сохранности миграции; функциональные проверки и фиксированные количества относятся к отдельной новой БД из [явных фикстур](../scripts/test-fixtures.mjs). Пользовательские занятия не менялись. Навигация также использует новую БД со случайными тестовыми паролями.

Журнал предыдущего dev-прогона заканчивался на `Compiling /dashboard/profile` без результата; в одном из других запусков порт уже был занят (`EADDRINUSE`). В ходе повторной проверки холодная компиляция заняла 74 304 мс. Tailwind-loader в копии проекта использовал рабочий каталог родительского процесса как область поиска классов, включая окружение прежних тестовых копий. В тестовой конфигурации область поиска явно ограничена `src` текущей копии; корень Turbopack для разрешения связанных зависимостей сохранён. В финальном прогоне холодный запрос занял 1 760 мс. Общие таймауты не увеличены, диагностические проверки не отключены.

Тест теперь выбирает свободный порт, следит за завершением собственного сервера и отдельно замеряет холодный запрос профиля. Полный dev-прогон повторён успешно: прежний таймаут не воспроизвёлся, ошибок Blocking Route / Instant нет. Исторический журнал не содержит профиля CPU, поэтому точное распределение времени в том старом зависшем процессе установить нельзя.

## Ограничения

Заявки, обработка услуг, редактирование из кабинета деканата, поиск студентов, журнал, оценки и пропуска не добавлялись. В существующем веб-интерфейсе никто не получил новых прав изменения персональных данных. Для будущих сотрудников нужна отдельная авторизация полномочий и назначений; техническая возможность записи фотографии сейчас доступна только доверенному оператору сервера. Неизвестные данные требуют поступления из официального источника. На основной БД не запускались reset или общий seed; применены только проверенная сохраняющая данные миграция и отдельный seed демонстрационных иллюстраций. Git commit не выполнялся.
