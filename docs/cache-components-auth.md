# Better Auth и Cache Components: исправление навигации

13 ноября 2026. Next.js 16.4.6, Better Auth 1.7.22. Исправление относится только к проверке доступа и границам загрузки защищённых кабинетов.

## Воспроизведение и причина

До исправления браузерный тест в `next dev` воспроизвёл оба предупреждения при прямом открытии кабинета студента, переходах по меню и возврате на главную:

- `Next.js encountered the unstable value new Date() while prerendering` — например, на `/dashboard/profile` и других страницах `/dashboard/[section]`;
- `Next.js encountered uncached data during prerendering or a navigation` — на `/dashboard`, в том числе после возврата из разделов.

Получено 14 сообщений в консоли браузера. Стек содержит `verifySignature` → `getSignedCookie` → `internalHandler` → `getCurrentUser` → `DashboardLayout`. Это не ошибка подписи или срока сессии: это диагностика Next.js при попытке выполнить request-time работу в предварительном рендере/проверке навигации.

`getCurrentUser` вызывал Better Auth после чтения `headers()`, но без явной границы до обращения к ленивому `auth.api`. Проверка сессии включает инициализацию библиотеки, Web Crypto, чтение БД и текущее время для срока действия. Такой результат не является статическим или пригодным для общей предзагрузки. `headers()` само по себе не обеспечивало нужного поведения в воспроизведённой проверке навигации этой версии Next.js.

Вторая часть проблемы — расположение `Suspense`. Граница в layout защищала прямую загрузку всего дерева. При переходе между его дочерними страницами общий layout сохраняется, и граница над ним не становится новой границей загрузки страницы. Для корней кабинетов не было `loading.tsx`; у студента была только более глубокая загрузка `/dashboard/[section]`, которая не покрывала возврат на `/dashboard`.

Это соответствует рекомендациям официальных руководств установленной версии:

- [Authentication with Cache Components](https://nextjs.org/docs/app/guides/authentication-with-cache-components): сессия читается в момент запроса за `Suspense`, а не включается в статическую оболочку;
- [Ensuring instant navigations](https://nextjs.org/docs/app/guides/instant-navigation): прямое открытие и переход под общим layout требуют соответствующих границ;
- [connection](https://nextjs.org/docs/app/api-reference/functions/connection): явное ожидание запроса перед выполнением динамической работы сторонней библиотеки.

## Выбранное решение

1. В [access.ts](../src/lib/access.ts) добавлено `await connection()` перед любым обращением к `auth.api`. Better Auth и последующая проверка актуальной роли выполняются только в request-time части рендера. Вызов `connection()` также не допускает случайного использования этого чтения внутри `use cache`.
2. Существующие `Suspense` вокруг авторизованной оболочки сохранены. Имя и прочие персональные данные не переносятся в статический интерфейс.
3. В каждом из четырёх корневых сегментов добавлен `loading.tsx`. Next.js создаёт границу вокруг дочерней страницы ниже общего layout, в том числе для возврата на главную. Все четыре используют одинаковый безопасный индикатор без персональных данных.
4. Проверки `requireRole` на страницах и около данных сохранены. Проверка layout не заменяет авторизацию отдельных страниц.

`instant = false` не использован: структурного исправления оказалось достаточно. Cache Components, Partial Prefetching и диагностика оставлены включёнными с прежними настройками. Сессии, токены и решения о доступе не помещались в `use cache`, `use cache: private`, `unstable_cache` или общий кеш. Существующий `React.cache()` только устраняет повторное чтение внутри одного серверного рендера.

При переходе внутри кабинета сохраняется оболочка, а новая страница может сразу показать индикатор загрузки. Персональный результат всё равно требует ответа сервера и свежей проверки сессии/роли; мгновенное отображение ранее закешированного решения о доступе не используется. При прямом открытии сначала доступен неперсональный fallback. Внешний вид загруженных страниц не менялся.

SEC-01 (лимиты входа), SEC-02 (абсолютные 8 часов и отсутствие продления), SEC-03 (подтверждённый выход) не изменены. Библиотеки и `node_modules` не редактировались.

- TypeScript: `npm.cmd run typecheck` — успешно.
- ESLint: `npm.cmd run lint` — успешно, без предупреждений.
- Production: `npm.cmd run build` — успешно; Cache Components и Partial Prefetching включены.
- Расписание: `npm.cmd run test` — успешно, включая границы публикации, персональный доступ, миграции и сохранность данных.
- Авторизация: `npm.cmd run test:auth` — успешно: четыре роли, пять аккаунтов, CSRF, лимиты, абсолютный TTL, выход при отказе хранилища, proxy/cookie, отказ доступа к чужим кабинетам.
- Браузер в `next dev`: `npm.cmd run test:auth:navigation` — успешно. Все четыре роли; прямое открытие; 30 разделов меню и возврат после каждого; сохранение документа при переходах; свежая роль из БД в той же сессии; редиректы из чужих кабинетов; выход и повторная проверка отозванной cookie. Оба предупреждения отсутствуют, ошибок браузера нет.
- Браузер в `next start`: `npm.cmd run test:auth:navigation -- --production` — тот же сценарий успешно прошёл для всех четырёх ролей. Ошибок и предупреждений нет.

Сценарий использует временную копию SQLite и случайные тестовые пароли. Для dev также копируется проект и используется отдельный кеш сборки: пользовательский сервер на порту 3000 остаётся нетронутым. Полный снимок основной БД сравнивается до и после выполнения — данные не изменились. Диагностика проверяется в консоли браузера, overlay и серверном журнале; тот же сценарий до исправления действительно фиксировал оба предупреждения.

## Повторная проверка

```powershell
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
npm.cmd run test
npm.cmd run test:auth
npm.cmd run test:auth:navigation
npm.cmd run test:auth:navigation -- --production
```

Браузерные проверки используют установленный Chrome и свободный порт 3210. Для Edge задайте `$env:PLAYWRIGHT_CHANNEL = 'msedge'`. При необходимости задайте другой `CABINET_TEST_PORT`. Не запускайте два экземпляра одного навигационного теста на одном порту.

Для ручной проверки в своём `next dev`: войдите каждой ролью, откройте кабинет напрямую, перейдите через меню в несколько разделов и каждый раз вернитесь на главную. Проверьте расписание студента/преподавателя, затем выход, вход другой ролью и попытки открыть чужой кабинет. В DevTools/консоли не должно быть предупреждений Blocking Route и Instant. Настройки диагностики для этого изменять не нужно.
