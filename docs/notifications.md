# Единая система уведомлений ЛКС

Реальные события всех кабинетов хранятся в одной системе Prisma/SQLite. Интерфейс студента использует прежний `/dashboard/notifications`, остальные роли — `notifications` своего кабинета. Демонстрационные карточки и старые новости не попадают в ленту и счётчики.

## Архитектура и права

- [notifications-repository.ts](../src/lib/notifications-repository.ts): создание события и адресных уведомлений, чтение, прочитанность, настройки и аудит.
- [notifications-sources.ts](../src/lib/notifications-sources.ts): сравнение значимых изменений БРС и эффективного расписания.
- [notifications-shared.ts](../src/lib/notifications-shared.ts): категории, DTO и проверка внутренних ссылок.
- [schema.prisma](../prisma/schema.prisma): `NotificationEvent`, `Notification`, `NotificationSettings`, `NotificationEmail`, `NotificationAudit`, `NotificationWriteState`.

`sourceKey` уникален для исходного события. Событие, адресаты и почтовый outbox создаются внутри той же транзакции, что изменение источника. Повтор уже завершённого события не меняет список адресатов и не создаёт доставку после изменения настроек. При откате изменения откатывается и уведомление. Отдельного опроса всей истории с повторной генерацией нет.

Внутренний `emitNotification` — серверный адаптер для доверенных подсистем. Клиентского API произвольного создания уведомлений, указания получателя или роли нет. [Учебные материалы](./materials.md) подключены через проверяемую серверную пакетную публикацию: источник MATERIALS, категория STUDY («Учёба»), актуальный доступ проверяется перед чтением и отправкой email. Фиктивные события не создаются.

Каждое адресное уведомление имеет монотонный `seq`, получателя, роль на момент доставки, безопасную ссылку и `readAt`. Общий event содержит источник, тип, категорию, краткий текст, обязательность и время. Лента упорядочена по `seq DESC`; время исходного события показывается пользователю. Серверные команды присваивают время при фиксации; backfill услуг вставляется по историческому времени.

Закрытый [API](../src/app/api/notifications/route.ts) использует Better Auth, абсолютный срок сессии и повторную проверку сессии после приёма тела. Все ответы, включая ошибки, имеют `private, no-store`, `Vary: Cookie`, `nosniff`. Изменения требуют точного Origin из `BETTER_AUTH_URL`; `cross-site` запрещён. Тело ограничено 4 КиБ и временем приёма. Страницы сами проверяют роль за Suspense; Cache Components и диагностические проверки сохранены.

Чтение, счётчик, массовое прочтение и почтовая доставка используют одинаковый актуальный scope:

- Только собственные адресные уведомления и текущая роль пользователя.
- БРС: опубликованный план своей группы либо своя история результатов, посещаемости, попыток или итогов — как в действующем журнале.
- Расписание студента: группа должна совпадать с группой адресата на момент события. После перевода старые уведомления прежней группы скрываются. Преподаватель получает только изменения занятий, где он действительно участвовал, в том числе сообщение о снятой замене.
- Услуги: владелец либо актуальный scope обработчика. [Общая проверка](../src/lib/services-permissions.ts) переиспользуется API услуг, лентой и почтовым worker: гранты, назначение деканата, воинские полномочия и закреплённый исполнитель. Отзыв гранта/назначения немедленно закрывает чтение соответствующих уведомлений и отправку писем.
- Объявления подразделения: текущая принадлежность студента к этому подразделению. Общие объявления доступны всем студентам.

Ссылка не даёт прав на объект: карточка заявления, БРС, расписание и публикация заново авторизуют запрос. В текст ленты и письма не копируются оценки, документы, воинские сведения или приватные комментарии. Значимые действия чтения, настроек и публикации фиксируются в `NotificationAudit`; исходные подсистемы сохраняют свой аудит.

## Подключённые источники и ссылки

| Источник | Реальные изменения | Глубокая ссылка |
| --- | --- | --- |
| Услуги | SUBMITTED, RESUBMITTED, IN_REVIEW, CLARIFICATION_REQUIRED, IN_PROGRESS, COMPLETED, REJECTED, STAFF_REPLY | `/dashboard/services?requestId=…`; для уполномоченных обработчиков — конкретное заявление в `/deanery/requests`, `/admin/requests`, `/staff/services` |
| БРС | Новый/изменённый/удалённый/восстановленный видимый результат или экзаменационная попытка; изменение официального итога/необходимости проверки; существенное изменение допуска | `/dashboard/grades?planId=…&eventId=…` открывает подробности работы; итоги/допуск — соответствующую дисциплину |
| Расписание | Публикация, перенос, замена, отмена, восстановление, снятие публикации; изменения времени, аудитории, дисциплины, вида, групп или преподавателей | Личное расписание студента/преподавателя с `week` и `day` |
| Объявления | Новая настоящая публикация через серверную команду администратора | `/dashboard/news?id=…` |

Услуги сохраняют прежний `ServiceEvent` и используют его ID как стабильный источник универсального события. При подаче и повторной подаче уведомляются также действующие уполномоченные обработчики. После закрепления исполнителя доступ других обработчиков к уведомлению прекращается вместе с доступом к заявлению. Старый `/api/services?view=events` сохранён для совместимости; лента и счётчики читают только универсальный API.

БРС сравнивает видимые данные до/после команды. Версии строк, приватные комментарии, настройки шкалы и повторный SAVE одинакового результата сами по себе уведомлений не создают. Затронутый студент определяется сервером по проверенной команде, а не клиентским получателем. Обычный экзамен учитывает официальный допуск, распределённый — академические условия последнего контроля. Пересчёт не является отдельным событием.

Расписание сравнивает эффективные опубликованные занятия до/после транзакции. Новые технические ID `Lesson` при одинаковом содержимом не вызывают рассылку. Получатели выбираются по действительной иерархии групп (`groupScope`, включая подгруппы) и старому/новому составу преподавателей. Перенос учитывает обе даты; изменения черновика не рассылаются. Роли деканата без назначения и после его отзыва не могут создавать такие изменения.

[Публикация объявления](../src/lib/announcements.ts) доступна администратору на `/admin/news`: заголовок, содержание, все студенты либо конкретное существующее подразделение. Публикация и адресные уведомления атомарны, повтор формы идемпотентен. Объявления подразделений исключены из публичного списка новостей; приватная страница проверяет принадлежность. Старые `News`, demo seed и запланированные вручную SQL-записи не сканируются и не рассылаются. Прямые SQL-изменения обходят серверные команды и не являются поддерживаемым способом публикации событий.

## Прочитанность, обновление и интерфейс

[NotificationsProvider](../src/components/notifications-provider.tsx) создаётся один раз в защищённой оболочке, отдельно для пользователя и роли. Меню, заголовок, главная и лента читают один store. Сетевые операции сериализованы; запросы обновления объединяются. Запоздавший GET не может затереть подтверждённую запись прочтения или более поздний ответ.

Обновление выполняется при открытии кабинета, фокусе/возвращении во вкладку, восстановлении сети, после действий услуг/БРС/расписания/публикации и каждые 12 секунд в видимой вкладке. Скрытая вкладка снимает периодический таймер. Между вкладками одного пользователя и роли `BroadcastChannel` передаёт только сигнал обновления, без данных сессии и содержания. Видимая вкладка обновляется, скрытая догружает при возвращении. В браузерах без BroadcastChannel остаются polling и обновление по фокусу.

Временный сетевой сбой сохраняет прежнюю ленту и показывает ошибку с повтором; следующий активный цикл восстанавливает данные. Истёкшая сессия очищает отображаемые данные. Общего серверного кеша сессий, токенов или разрешений нет.

`GET /api/notifications` возвращает первые 30 записей, `unread`, `boundary`, `nextCursor`. Следующая страница — `?before=seq`, без offset: вставка новых событий не сдвигает старые страницы. При polling перечитывается уже открытая часть ленты. Категории показаны только компактными подписями, фильтров и вкладок нет.

Открытие списка ничего не отмечает. Переход по ссылке вызывает `READ` только для выбранного ID. «Прочитать все» передаёт `boundary` последнего полученного снимка и меняет только собственные доступные непрочитанные строки с `seq <= boundary`; появившиеся позднее события остаются новыми. Счётчики и состояние обновляются без перезагрузки страницы. Отдельных кнопок прочтения у карточек нет.

## Настройки

[Блок настроек](../src/components/notification-settings.tsx) находится в профиле каждой роли. Настройки сохраняются в БД:

- Необязательные категории в ЛКС (по умолчанию все включены).
- Отдельный флаг личного email и категории писем (по умолчанию выключены).
- Обязательные события учёбы, расписания и заявлений продолжают поступать независимо от необязательных категорий. Email всегда доброволен.

Изменение категорий влияет на новые события и отправку ещё не доставленных писем, не удаляет историю. Интерфейс честно сообщает отсутствие провайдера либо неподтверждённый email. Выбор желаемых настроек можно сохранить заранее; это не активирует недоступный канал. Самостоятельного подтверждения email в проекте пока нет: используется только существующий доверенный `User.emailVerified`, который пользователю нельзя менять через этот API. Университетские ящики не генерируются.

## Почтовый адаптер и worker

[notifications-email.ts](../src/lib/notifications-email.ts) отделяет `NotificationMailAdapter` от outbox. Первая реализация использует Nodemailer 10.6.0 с собственными TypeScript-типами и настоящий SMTP. Версия зафиксирована в lock-файле; отдельный пакет `@types/nodemailer` не нужен. `PERSONAL_EMAIL` означает подтверждённый email учётной записи; `UNIVERSITY_EMAIL` зарезервирован, активных отправок туда нет.

Переменные окружения описаны в [.env.example](../.env.example):

```dotenv
NOTIFICATIONS_SMTP_HOST=smtp.example.test
NOTIFICATIONS_SMTP_PORT=587
NOTIFICATIONS_SMTP_SECURE=false
NOTIFICATIONS_SMTP_FROM=notifications@example.test
# NOTIFICATIONS_SMTP_USER=
# NOTIFICATIONS_SMTP_PASSWORD=
```

На production необходим HTTPS `BETTER_AUTH_URL`. Порт 587 использует обязательный STARTTLS, `SECURE=true` — TLS с начала соединения (обычно 465). Сертификат обязательно проверяется. Пароль SMTP отдельный от Better Auth; он не сохраняется в БД и не выводится в лог. Только тестовый loopback SMTP может работать без TLS при явном `NOTIFICATIONS_SMTP_LOCAL_TEST=true`.

Worker:

```sh
npm run notifications:deliver
```

Команда обрабатывает до 25 готовых писем и завершается. На VPS её следует запускать отдельным timer/cron, например раз в минуту, с тем же окружением и БД. Она не выполняется в GET ленты и не задерживает пользовательские операции. Пока провайдер не настроен, возвращает `available: false`, очередь остаётся сохранённой. Наличие настроек не является проверкой внешней доставляемости.

Состояния: `pending`, `sent`, `failed`. Ограничение — 4 попытки с паузами 1/2/4 минуты. После исчерпания запись остаётся `failed`; бесконечных повторов нет. Два worker используют атомарный claim с двухминутной lease и проверкой счётчика попыток. Просроченная lease допускает восстановление после аварии. Перед отправкой повторно проверяются текущий адрес, его подтверждение, настройки, роль и доступ к источнику. Отозванная доставка завершается `failed/DELIVERY_NOT_ALLOWED`, без сетевого обращения.

В письме только фиксированный шаблон категории и защищённая ссылка. Заголовок/текст исходного события не используются, вложений нет. `sent` выставляется только после подтверждённого SMTP-приёма адресата; это подтверждает приём провайдером, а не попадание в конечный ящик. В ошибках хранится только безопасный код, без ответов SMTP, адресов и паролей.

SMTP не обеспечивает строгое exactly-once: если сервер принял письмо, а процесс завершился до записи `sent`, повтор может доставить письмо снова. Стабильный `Message-ID` помогает дедупликации у получателя, но не гарантирует её. Ошибка почты никогда не отменяет уведомление внутри ЛКС. Для строгой дедупликации внешней доставки в будущем нужен провайдер с идемпотентным API.

## Миграция и эксплуатация

Добавлена [20261118120000_notifications](../prisma/migrations/20261118120000_notifications/migration.sql): только новые таблицы и два nullable поля `News`. Прежние таблицы, данные, пароли, оценки и расписание сохраняются. Исторические `ServiceEvent` входят в ленту один раз, как уже прочитанные, с прежним временем. Для них не создаются письма. Новости и БРС не backfill-ятся.

[prepare-notifications.mjs](../scripts/prepare-notifications.mjs) выполняет `VACUUM INTO`, проверяет integrity/FK, пробную миграцию на второй копии, сохранность всех старых полей/строк и повторный deploy. Перед `--apply` сравнивает основную БД с согласованной копией. При конкурентных изменениях отказывается продолжать; на production на время применения нужно остановить запись приложения. `migrate reset` не используется. Резервные копии остаются только в игнорируемом приватном `.local/`.

```sh
node --env-file-if-exists=.env scripts/prepare-notifications.mjs
npm run db:notifications
npm run typecheck
npm run lint
npm run build
npm run test:notifications
npm run test:services
npm run test:services:ui
npm run test:brs
npm run test:schedule:editor
npm test
npm run test:auth
npm run test:auth:navigation
npm run test:auth:navigation -- --production
```

Команды генерации Prisma/Next и сборки запускать последовательно. Проверки создают изолированные БД/учётные данные; основная БД сравнивается до и после. [verify-notifications.mjs](../scripts/verify-notifications.mjs) использует настоящий локальный тестовый SMTP и Chrome через Playwright, сохраняет отчёт и снимки 360/1366 px в приватном `.local/notifications-test-*`.

SQLite-специфичны миграционный SQL, `AUTOINCREMENT`, согласованное копирование и сериализация записи. Бизнес-логика использует Prisma. Для PostgreSQL нужны отдельная сохраняющая данные миграция, sequence, адаптер и проверка конкурентных транзакций; Windows `node_modules`/база не переносятся вместо установки и миграции на Linux.

## Границы дальнейшей работы

Не подключены внешний production SMTP, университетские ящики, самостоятельное подтверждение личного email, IMAP/webmail, push/WebSocket и общежитие. Для общежития подготовлена категория, но нет фиктивной генерации. [Материалы](./materials.md) используют общую ленту и email-outbox, без отдельной очереди. Не реализованы политика удаления/архивации уведомлений и административный повтор исчерпанных почтовых попыток. Очень большие списки адресатов и длительные учебные периоды пока обрабатываются внутри транзакции; для больших вузов потребуется пакетный transactional outbox/fan-out без изменения контракта ленты.
