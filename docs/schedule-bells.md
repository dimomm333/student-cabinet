# Две сетки звонков

Обе сетки, обед и большой перерыв хранятся в [schedule-bells.ts](../src/lib/schedule-bells.ts). `identifyPair` сравнивает оба конца интервала точно; при общем интервале выбирается сетка А. Третья пара различается: А — 12:25–13:55, Б — 11:50–13:20. Сетка не назначается университету, группе или преподавателю глобально.

[ScheduleTimeFields](../src/components/schedule-time-fields.tsx) используется общей формой регулярных занятий, дополнительных пар, замен и переносов. Существующий нестандартный интервал открывается в ручном режиме без округления. Стандартный и ручной режимы сохраняют отдельные значения до закрытия формы. При первом переходе новой формы в ручной режим подставляется выбранная стандартная пара.

[LessonCard](../src/components/schedule-view.tsx) показывает номер в публичном, студенческом, преподавательском расписании, редакторе и блоке ближайших занятий. Для нестандартного интервала номер отсутствует. Существующие метки отмен, замен и переносов сохранены. В списках редактора номер добавлен через общий форматтер.

Prisma, миграции, хранимые занятия, авторизация, учебные недели, алгоритм конфликтов и поля REST API v1 не изменены. Выбор сетки — только способ заполнить прежние поля начала и окончания; сервер проверяет пересечение фактических интервалов.

## Проверки

- `npm run test:schedule:bells` — все 14 интервалов, обед, перерыв, различие третьих пар, точное совпадение и нестандартное время.
- `npm run test:schedule:editor` — изолированная SQLite-копия; все варианты формы, ручной ввод и сохранение черновика при переключении, открытие старого нестандартного времени, стандартная регулярная пара Б и замена на А, дополнительная стандартная пара на мобильном устройстве, публичное и персональное отображение, конфликты разных сеток, права деканата и сохранность исходной БД. Сценарий сохраняет desktop/mobile скриншоты.
- `npm run test`, `npm run test:api` — общие регрессии расписания и контракт API. Эти старые сценарии ожидают базовые демонстрационные данные (5 занятий ПИ-24-1). При запуске на копии текущей рабочей БД ожидание не выполнилось: 7 вместо 5. Повторный прогон выполнен успешно с `DATABASE_URL`, указывающим на отдельную SQLite-копию, из которой удалены только дополнительные тестовые занятия и разовые изменения. Рабочая БД не редактировалась.
- `npm run test:schedule:browser` — desktop/mobile, публичное расписание, кабинеты и ближайшие занятия; успешно.
- `npm run test:auth` — все пять ролей, SEC-01/02/03, CSRF, отзыв сессии и сохранность исходных данных; успешно.
- `npm run typecheck`, `npm run lint`, `npm run build` — успешно.
- `npm run test:auth:navigation -- --production` — успешно на отдельном порту 3232: все пять ролей, прямое открытие, меню, возврат, смена роли, чужие кабинеты и выход; предупреждений Blocking Route / Instant и ошибок браузера нет, исходная БД сохранена.

Навигационные проверки dev и production следует запускать последовательно либо на разных `CABINET_TEST_PORT`: стандартный порт у них общий.

`npm run test:auth:navigation` в dev не завершён успешно: после повторного запуска на отдельном порту 3231 Turbopack остановился на `Compiling /dashboard/profile`, браузер получил timeout 120 секунд. В первом запуске также был конфликт общего тестового порта. Это ограничение проверки; отсутствие Blocking Route / Instant в dev не подтверждено. В production тест редактора проверяет отсутствие этих предупреждений и ошибок браузера.
