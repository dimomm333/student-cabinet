# Электронные услуги — серверная система и интерфейс

Реализованы серверная система и интерфейс в существующих Next.js 16.4.6, Prisma/SQLite и Better Auth. Пользователи и подразделения общие с остальным ЛКС. Студенческий каталог, индивидуальные формы, черновики, документы, уточнения, переписка, очереди сотрудников и уведомления работают через `/api/services`. Новых миграций для интерфейса не потребовалось.

Все основания, названия полей и требования к приложениям — **демонстрационные**, не юридические требования университета. Перед эксплуатацией их необходимо согласовать с вузом.

## Фотографии в заявлениях на общежитие

В заявлениях «Заселение в общежитие» и «Переселение в общежитии» можно добавить несколько необязательных фотографий. Кнопка «Прикрепить фотографии» открывает выбор файлов. До сохранения форма показывает местный предпросмотр, имя и размер каждого файла. После нажатия «Сохранить фотографии» выбранные файлы по очереди загружаются в черновик. Их можно снять до подачи заявления. Повторная загрузка уже прикреплённого снимка не создаёт вторую запись.

Слот `housing-photos` использует существующую модель `ServiceDocument` и закрытое хранилище. Допускаются JPEG, PNG и статический WebP до 8 МиБ на файл и до 20 мегапикселей. Общий лимит заявления составляет 20 активных вложений. Сервер проверяет подпись, расширение, MIME и декодируемость изображения, затем перекодирует его без метаданных. Предпросмотр сохранённого снимка выдаётся по защищённому маршруту `/api/services?view=photo&id=…` для владельца или сотрудника с доступом к заявлению и правом `readFiles` в соответствующем подразделении. Снятые приложения остаются в истории по действующим правилам.

Открытая карточка заявления проверяет статус в фоне. При несохранённом вводе фоновое обновление приостанавливается. При конфликте доступно действие «Обновить версию, сохранив мой ввод». Если загрузка завершилась, но список вложений прочитать не удалось, можно повторить чтение списка.

Сервер валидирует по доверенной конфигурации кода и версии, а не по присланной схеме. Для изменения правил добавляется новая версия в реестр с сохранением прежней; существующую версию нельзя переписывать. Seed создаёт отсутствующие версии, не меняет существующие определения, флаги, заявления и полномочия.

## Модели

В [schema.prisma](../prisma/schema.prisma) добавлены:

- `ServiceRoute`: конкретная услуга + исходный AcademicDepartment → подразделение обработки. Нет активного маршрута — отправка запрещена, черновик доступен.
- `ServiceGrant`: явное полномочие пользователя на услугу **или** категорию в подразделении обработки, флаги `readFiles`, `readMilitary`, `active`.
- `ServiceRequest`: владелец, код/версия схемы, статус, версия записи, поля, официальный снимок, подразделение, принявший сотрудник, уточнения, результат и даты. Удаление черновика мягкое.
- `ServiceDocument`: случайный ключ хранилища, размер/тип/хеш, автор, слот, вид STUDENT/RESULT, дата удаления из активных приложений.
- `ServiceHistory`: неизменяемая история с автором, именем, датой, действием, текстом и закрытыми снимками версий/полей/документов.
- `ServiceReceipt`: ключ идемпотентности в пределах пользователя, хеш команды и минимальный результат. Повтор с изменёнными данными отклоняется.
- `ServiceWriteState`: сериализация команд транзакцией. Решение о правах, версия, изменение, история, событие и receipt находятся в одной транзакции.
- `ServiceEvent`: адресные события для подключения существующего раздела уведомлений на этапе 2. Уникальность `(requestId, version, type)` предотвращает дубли.
- `MilitaryRecord`: отдельная закрытая модель; студент читает только свою запись, сотрудник — только с явным полномочием. API изменения нет.

Действующие БРС, фотографии, расписание, профили и сессии не меняются. Связи `User` и `AcademicDepartment` дополнены обратными отношениями. Ограничения внешних ключей сохраняют историю.

## API

Единый закрытый [Route Handler](../src/app/api/services/route.ts): `/api/services`. Ответы, включая ошибки, имеют `Cache-Control: private, no-store`, `Vary: Cookie`, `nosniff`. Runtime Node.js, `connection()` до Better Auth; общий кеш не используется. POST требует точного Origin из `BETTER_AUTH_URL`; чужой `Sec-Fetch-Site` отклоняется. Права и абсолютный срок действующей сессии повторно проверяются у данных, в том числе после загрузки тела.

| Метод/параметры | Назначение |
| --- | --- |
| GET (view=catalog по умолчанию), q | Каталог с ранжированием, схемами, доступностью и настроенным подразделением |
| GET view=suggest&q=... | Та же локальная поисковая основа перед общим обращением |
| GET view=request&id=...&page=0 | Заявление, профильный preview, файлы и история |
| GET view=requests&page=0&code=...&status=...&from=YYYY-MM-DD&to=YYYY-MM-DD | Собственные заявления / разрешённая очередь; `to` включает весь день UTC |
| GET view=file&id=DOCUMENT_ID | Авторизованное скачивание без публичного URL |
| GET view=events&page=0 | Только собственные серверные события; UI доставки ещё не подключён |
| GET view=military&studentId=... | Собственная запись или явно разрешённый просмотр сотрудником |
| GET view=militaryProfile | Собственные сведения студента и доступность услуги, без подмены владельца |
| POST application/json | CREATE, SAVE, DELETE, SUBMIT, TRANSITION, COMMENT, REMOVE_FILE |
| POST ?upload=1&id=...&version=N&requestId=...&slot=...&kind=STUDENT | Бинарная загрузка; сотрудник использует kind=RESULT, slot=result |

Пагинация: 50 записей, `page` от 0 до 99999; стабильная сортировка с id. В ответе списка есть `total`. В деталях `page` независимо сдвигает историю и список файлов на 50. Поля и документы доступны только через детали после проверки прав. История хранит текст как текст, без HTML; будущий UI обязан использовать обычный React-рендер текста, не `dangerouslySetInnerHTML`.

Все JSON-команды имеют `operation`, `requestId` (16–100 латинских букв, цифр, `_`, `-`). Каждое изменение существующего заявления требует `id` и текущую числовую `version`. Конфликт версии/статуса/ключа — 409. Ошибки валидации — 400, сессии — 401, Origin — 403, чужие/недоступные ресурсы — 404, размер — 413, формат тела — 415, технический отказ — 503. Повторять технически неудавшуюся команду следует с тем же ключом и телом. После конфликта версии нужно заново получить детали.

```json
{"operation":"CREATE","requestId":"unique-request-key-0001","code":"study-certificate"}
```

```json
{"operation":"SAVE","requestId":"unique-request-key-0002","id":"request-id","version":1,"fields":{"purpose":"По месту требования","copies":1,"delivery":"Лично"}}
```

SAVE — частичный patch. Пустая строка/null очищает поле; неизвестные и защищённые поля отклоняются. В черновике обязательность не проверяется; типы, варианты, длины, даты и порядок периода проверяются всегда. SUBMIT проверяет все обязательные поля и активные приложения по версии услуги.

Перед SUBMIT клиент получает `profilePreview.values` и `confirmationHash` из деталей, показывает студенту сведения и предлагает подтвердить актуальность. Команда отправки содержит `confirmed: true` и этот `confirmationHash`. Несовпадение с текущими серверными данными отклоняется. Неправильные данные исправляются через `personal-change`, защищённые поля профиля в обычной форме менять нельзя. Система использует только реально имеющиеся ФИО/группу и необходимые реквизиты. Паспортов в текущей модели профиля нет. Снимок при первой отправке сохраняется навсегда; последующие изменения профиля его не заменяют, включая циклы уточнения. Актуальный preview при повторной подаче проверяется отдельно.

TRANSITION принимает `status`, `text`; для уточнения дополнительно `clarificationFields` и/или `clarificationSlots`. COMMENT принимает `text`, REMOVE_FILE — `documentId`. Тексты до 4000 символов. JSON ограничен 32 КиБ, тело читается с лимитом и таймаутом 15 секунд.

## Переходы и переписка

```text
DRAFT → SUBMITTED → IN_REVIEW → IN_PROGRESS → COMPLETED
                        ↓           ↓
                 CLARIFICATION_REQUIRED → IN_REVIEW
                        ↑           ↓
                        └───────────┘
IN_REVIEW / IN_PROGRESS → REJECTED
```

В уточнение можно перейти из IN_REVIEW и IN_PROGRESS. Сотрудник обязан оставить понятный комментарий и список разрешённых к исправлению полей/слотов. Студент может менять только их, затем повторно отправляет всё заявление после полной валидации. Количество циклов не ограничено. Первоначальные и последующие версии остаются в истории.

При принятии SUBMITTED → IN_REVIEW сотрудник становится `assigneeId`, после чего другим обработчикам это заявление не выдаётся. Комментарии доступны обеим сторонам после подачи до терминального решения. Отказ требует причины; исполнение требует текста результата и фиксирует сотрудника/время. Итоговый файл можно приложить в IN_PROGRESS. Сервер не создаёт фиктивные справки; факт исполнения не требует наличия электронного файла, поскольку результат может быть выдан лично.

COMPLETED и REJECTED терминальные. Обычного API изменения или переоткрытия нет. Исполнение услуги фиксирует решение. Для выдачи нового QR по исполненному заявлению «Перевыпуск пропуска» оператор отдельно подтверждает операцию в разделе [«Электронные пропуска»](./student-passes.md). Официальные данные, фотография и выплаты по-прежнему обслуживаются своими процедурами.

## Полномочия

STUDENT работает только со своими заявлениями и документами. TEACHER не допускается к обработке. ADMIN, TECHNICAL_STAFF и DEANERY_STAFF требуют явных ServiceGrant; общая роль не даёт обхода. Деканат дополнительно требует действующего `DeaneryDepartmentAssignment` на подразделение обработки. Похожие названия/факультеты не дают прав. Отзыв назначения, гранта, смена роли или удаление сессии учитывается при следующей операции.

`readFiles` нужен для списка и скачивания документов, а также операций сотрудника с файлами. `readMilitary` обязателен для доступа к заявлениям military-change, включая их историю и снимки. Прямой просмотр MilitaryRecord дополнительно требует грант именно на military-change в подразделении записи. Финансовая категория назначается отдельным уполномоченным обработчикам из существующих ролей, новая роль не создаётся. Отсутствие назначения закрывает очередь.

## Файлы

[services-storage.ts](../src/lib/services-storage.ts) изолирует `ServiceStorage.put/get/remove`; локальная реализация использует `SERVICES_STORAGE_DIR`, по умолчанию `.local/service-documents`. Каталог должен находиться вне `public/` и не раздаваться веб-сервером. Пути строятся Node.js, на Linux создаются каталог 0700 и файлы 0600; на Windows права доступа регулируются ACL системы. Приватное хранилище и его резервные копии не следует включать в Git.

**Текущий allowlist — PNG/JPEG до 8 МиБ и PDF до 20 МиБ**, до 20 активных файлов заявления. Для PDF используется отдельный ограниченный процесс, подробности и ограничения — в разделе доработок ниже. Исходный принятый PDF сохраняется без преобразования; изображения по-прежнему перекодируются в PNG.

Проверяются имя без пути, расширение, заявленный MIME, сигнатура и успешное декодирование Sharp с лимитом 20 млн пикселей. Содержимое полностью перекодируется в PNG без исходных метаданных. Имя передаётся в заголовке `X-File-Name: encodeURIComponent(filename)`, тело — бинарное, `Content-Type` строго image/png или image/jpeg. Внутренний UUID не связан с именем. Файлы отдаются как attachment с CSP sandbox, после проверки сессии/владельца/полномочия; размер и SHA-256 проверяются при скачивании.

Запись файла и fsync завершаются **до** транзакции метаданных. Неудавшаяся запись не создаёт успешную операцию. При отказе БД файл удаляется только после проверки отсутствия committed-ссылки; при недоступной БД безопаснее сохранить возможный orphan. Повтор загрузки с тем же ключом и содержимым не добавляет вторую запись, временный новый blob удаляется.

Удаление/замена приложения выполняется REMOVE_FILE и UPLOAD с актуальными версиями. Снятые файлы сохраняются для истории и доступны разрешённым адресатам заявления. Они исключаются из обязательных приложений при отправке. Автоматического физического удаления и политики хранения пока нет; будущая очистка обязана сохранять документы, упомянутые историей. При удалении черновика все его файлы становятся недоступны через API. Для восстановления после аварии возможные файлы без метаданных требуют закрытой сверки оператором; это не выдаётся за готовый garbage collector.

## Поиск и события уведомлений

С 18 ноября 2026 события услуг интегрированы в [единую систему уведомлений](./notifications.md). `ServiceEvent` сохранён как источник; новая лента, постоянная прочитанность, общий счётчик, polling каждые 12 секунд, настройки профиля и SMTP-outbox описаны в этом документе. Старые события перенесены один раз как прочитанные, без исторических писем. При подаче/уточнении уведомляются также текущие уполномоченные обработчики; права проверяются общей функцией услуг при чтении ленты и перед email. Старое описание интерфейса этапа 2 ниже сохранено как история реализации.

Поиск локальный: нормализация регистра/ё, взвешенные совпадения названия и скрытого словаря, простые русские словоформы и расстояние редактирования ≤ 1 для слов от четырёх символов. [Поисковый словарь](../src/lib/services-search-dictionary.ts) обновляется независимо от неизменных конфигураций исторических форм. Каталог и подсказки используют одну функцию; неоднозначные слова имеют меньший вес.

Ранее существовавшие уведомления были статическими демонстрационными данными. Адресные серверные события SUBMITTED, RESUBMITTED, IN_REVIEW, CLARIFICATION_REQUIRED, IN_PROGRESS, COMPLETED, REJECTED, STAFF_REPLY теперь подключены к тому же разделу `/dashboard/notifications` и виджету на главной. События сохраняются атомарно с действием, не содержат паспортов, документов и текста причины отказа: причина читается в защищённой истории. GET view=events отдаёт только собственные события и рабочую ссылку `/dashboard/services?requestId=...`. Компонент обновляет список при открытии, возврате фокуса окна, кнопке «Обновить» и собственных действиях с заявлениями. Постоянного push-канала нет. Демонстрационные уведомления кампуса сохранены в явно подписанном раскрывающемся блоке; фиктивные счётчики «3» в меню и заголовке убраны. Второй независимой страницы уведомлений нет.

## Миграция и команды

Добавлена сохраняющая данные миграция `20261116120000_services`. Подготовка [prepare-services.mjs](../scripts/prepare-services.mjs) использует существующие функции снимков: integrity, VACUUM INTO, проверку миграции на копии, побайтовую сверку всех прежних полей/записей и повторный seed. Перед применением следует остановить запись приложения: скрипт обнаруживает изменения со времени резервной копии и отказывается продолжать. Изменения не включают migrate reset или перезапись demo-профилей/паролей. Новая БД также создаётся обычной последовательностью migrate deploy + seed-services.

npm run typecheck
npm run lint
npm run build
npm run test:services
npm run test:brs
npm run test:auth
npm run test:auth:navigation

### Формы, черновики и документы

Форма поддерживает текст, числовые поля/суммы/даты, варианты выбора, обязательность и ограничения из конфигурации. Для причины перевыпуска пропуска есть подсказки с возможностью собственного текста; KEEP/NEW показаны понятными русскими названиями. Слот новой фотографии появляется только при NEW. Обязательные приложения/поля окончательно проверяются сервером. Официальная фотография не меняется при отправке или исполнении.

Частично заполненный черновик сохраняется автоматически с задержкой 650 мс, при уходе с поля и внутренних переходах. Успешно сохранённые поля читаются из БД после обновления, нового входа и с другого устройства. Статусы: «Сохранение…», «Сохранено», «Не удалось сохранить». Аварийная копия полей хранится в sessionStorage вкладки на 30 минут с привязкой к аккаунту; файлы в неё не включаются. Ограничения закрытия браузера описаны ниже.

Изменения полей отправляются последовательно, без блокирования ввода на время автосохранения. Остальные операции ждут текущего сохранения и используют его версию. Неопределённый сетевой результат SAVE повторяется с прежними телом и requestId; новые поля сохраняются следующей командой. Конфликт с другой вкладкой останавливает запись до явного обновления версии и проверки ввода. Отправка ждёт последних изменений; удаление останавливает автосохранение, серверная мягкая отметка удаления запрещает поздние записи.

Перед отправкой показан `profilePreview`, ссылки на исправление данных и подтверждение `confirmed`/`confirmationHash`. Защищённые профильные данные недоступны для прямого редактирования; отсутствующие паспортные сведения не выдумываются. Если профиль изменился после просмотра, нужна повторная проверка. После отправки показывается сохранённый официальный снимок, а не новые данные профиля.

Загрузки автоматически запускаются сразу после выбора файла через тот же бинарный API и X-File-Name. PNG/JPEG — до 8 МиБ, PDF — до 20 МиБ. XMLHttpRequest upload progress показывает название, размер, проценты и полосу; 100% передачи сменяются состоянием «Обрабатывается», а «Загружен» появляется только после успешного ответа сервера. Список приложений обновляется автоматически. Прерванную загрузку нужно повторить выбором файла; бинарные данные локально не сохраняются. Снятие и замена по-прежнему выполняются последовательными версионируемыми REMOVE_FILE/UPLOAD; история и закрытые ссылки сохранены.

### Обработка и уведомления

Очереди имеют фильтры услуги, статуса и периода, пагинацию, номер/дату подачи/обновление. Принятие в рассмотрение закрепляет сотрудника. Для уточнения выбираются конкретные поля/слоты и вводится обязательное объяснение. Для отказа обязательна причина, для исполнения — текст результата. В IN_PROGRESS уполномоченный сотрудник может приложить готовый документ. Терминальные карточки доступны только для чтения. Переписка и история выводят текст безопасно с переносами, без вставки HTML; историю можно догрузить полностью страницами.

События отображаются в существующих уведомлениях и главном виджете. Их текст содержит тип события, сокращённый номер и дату, но не документы, воинские сведения или закрытые комментарии. Ссылка открывает карточку, где сервер заново проверяет владельца. События не дублируются при повторных командах. Прочитанность не моделируется: UI не выдаёт количество событий за число непрочитанных, новых миграций ради этого нет.

### Автосохранение и аварийное восстановление

[services-request-screen.tsx](../src/components/services-request-screen.tsx) ведёт очередь SAVE для всех 16 форм. Черновик создаётся кнопкой «Создать черновик» либо подтверждённой кнопкой обращения внизу каталога. Поля сохраняются с debounce 650 мс, при blur, внутренних ссылках, pagehide, скрытии вкладки и перед выходом. SAVE использует keepalive, однако браузер не обязан завершить запрос при аварийном закрытии. При выходе ожидание ограничено двумя секундами, после чего выполняется прежний подтверждённый серверный выход.

Сетевой сбой не стирает ввод; для SAVE предусмотрены три отложенных повтора, событие online и ручное повторение. Версия и идемпотентный ключ сохраняются вместе с неопределённой командой. Нельзя автоматически сливать конфликт с другим устройством: интерфейс сохраняет локальный ввод и предлагает явно загрузить актуальную версию. Повторный SUBMIT перед отправкой перечитывает официальный профиль и проверяет confirmationHash. Официальные записи при исполнении не изменяются.

[services-recovery.ts](../src/lib/services-recovery.ts) использует только sessionStorage: аварийный ввод и неопределённая SAVE-команда имеют срок 30 минут и ключ аккаунта/заявления. При чтении удаляются просроченные копии и копии других аккаунтов; при подтверждённом выходе и ответе 401 копии очищаются. При успешном сохранении, удалении и отправке копия заявления удаляется. Это уменьшает следы на общем компьютере: постоянного localStorage, токенов и бинарных файлов нет. Хранилище вкладки доступно скриптам того же origin; это не зашифрованное долговременное хранилище. Если браузер запрещает storage, работает серверное сохранение.

**Граница гарантии:** после полного закрытия браузера, аварии ОС, удаления данных сайта или истечения 30 минут гарантированно восстанавливаются только подтверждённые сервером поля. Последние изменения до завершения SAVE могут потеряться, если sessionStorage не восстановлен браузером. Незавершённый файл не считается сохранённым; после возвращения показывается пояснение о проверке списка и повторном выборе файла. Невозможно гарантировать доставку при выключении устройства. Для надёжного перехода на другое устройство дождитесь «Сохранено».

### PDF и ограничения проверки

[services-storage.ts](../src/lib/services-storage.ts) сохраняет исходные PDF и SHA-256 в прежнем приватном хранилище. Приём HTTP-тела ограничен во время чтения: 8 МиБ для изображений, 20 МиБ для PDF, тайм-аут 15 секунд. Проверяются имя, расширение, MIME, сигнатура, структура и завершение PDF. PDF никогда не передаётся в Sharp как изображение. Вложенные JPEG-потоки отдельно декодируются Sharp с лимитом пикселей. Старые изображения не удаляются.

[validate-service-pdf.mjs](../scripts/validate-service-pdf.mjs) принимает PDF 1.0–1.7 и использует зафиксированный pdf-lib 1.17.1 в отдельном процессе: 8 секунд, V8 heap 128 МиБ, не более двух процессов одновременно, 20 000 объектов, глубина обхода 60, 150 000 узлов, 200 страниц. Перед аллокацией ограничивается декомпрессия потоков: 16 МиБ на буфер, 64 МиБ суммарных выделений; JPEG — 20 млн пикселей на изображение и 40 млн на документ. Контроль аллокаций адаптирован к внутреннему DecodeStream именно закреплённой версии; при обновлении библиотеки обязательны повторные проверки защиты от decompression bomb. Heap-limit не является лимитом всей RSS: бинарные буферы и Sharp используют внешнюю память, ограниченную отдельно размерами/пикселями. Размеры страниц также ограничены. stdout/stderr парсера с содержимым не публикуются.

Объектные потоки разбираются библиотекой, после чего проверяются все разрешённые объекты и ссылки. Отклоняются шифрование, JS/действия открытия, внешние ссылки и потоки, вложенные файлы, формы/XFA, мультимедиа/3D и неподдерживаемые кодеки (включая JPEG2000, JBIG2 и факс). Flate/LZW/ASCII85/ASCIIHex/RunLength и отдельные DCT/JPEG поддерживаются в пределах ресурсов. Некоторые корректные сложные PDF будут отклонены намеренно; можно предоставить обычный PDF без активных элементов или PNG/JPEG. Проверяется структура и декодируемость поддерживаемых потоков, без рендеринга документа.

**Это не антивирусная проверка и не гарантия отсутствия любого вредоносного содержимого или уязвимостей PDF-просмотрщика.** Для эксплуатации нужна отдельная антивирусная обработка/карантин. PDF выдаётся только после прежних серверных проверок полномочий, как attachment, с private/no-store, nosniff и CSP sandbox, без встроенного предпросмотра. Запись blob до транзакции, cleanup при неудаче, receipts, история и проверка владельца сохранены. Скрипт и зависимости включены в outputFileTracing для deployment; на Linux нужен обычный npm ci и build, без переноса Windows node_modules.

## Загрузка PDF и удаление из списка черновиков — 16 ноября 2026

### Установленная причина и границы воспроизведения

Исходный PDF руководства HONOR в проекте отсутствует, поэтому именно его содержимое не проверялось. На одном и том же корректном тестовом PDF воспроизведён отказ серверной проверки имени: русское имя с обычными скобками принимается, добавление `&`/`,` даёт ServiceError 400 «Тип файла не совпадает с содержимым или некорректное имя PDF», имя длиной 175 символов также отклоняется прежним пределом 120. Это происходит до запуска PDF-парсера. XHR к этому моменту уже передал все байты, поэтому показывает 100%; процент не означает успешное сохранение. Старые события добавления/снятия документов относятся к отдельным ранее подтверждённым операциям и не доказывают успех текущего запроса.

Имя теперь допускает кириллицу, пробелы, `_ ( ) , & . -`, до 255 символов. Пути, `..`, управляющие и прочие недопустимые символы запрещены. Имя используется только как метаданные; приватный blob сохраняется под UUID. Заголовок имени по-прежнему URL-кодируется и декодируется на сервере. MIME, расширение, сигнатура, структура PDF и прежние полномочия проверяются независимо.

Дочерний валидатор возвращает только короткий код отказа без содержимого: повреждённая структура, неподдерживаемое содержимое (включая ссылки/интерактивность), шифрование, ресурсные лимиты. Клиент получает понятное соответствующее сообщение. Лимиты размеров, времени, памяти, декомпрессии и запрет активных элементов сохранены. PDF со ссылками и интерактивными элементами намеренно отклоняется; проверки ради загрузки руководства не отключались.

После успешного UPLOAD индикатор исчезает, а обновление списка повторяется только безопасными GET (до трёх попыток). При продолжающемся сбое показано «Документ сохранён… Повторно загружать файл не нужно» и доступно обычное «Обновить данные». ## Диагностика повторного отказа JPEG — 16 ноября 2026

### Подтверждённая причина воспроизведённого отказа

Через Chrome **до изменения кода** воспроизведена вся последовательность: вход студентом → создание deanery-appeal → ввод нескольких полей с автосохранением → выбор валидного JPEG примерно 3 МиБ с обычным именем. [Безопасный отчёт до исправления](../.local/services-ui-d7oF06/jpeg-before.json): XHR UPLOAD получает **HTTP 413**, тело содержит «Изображение после безопасного преобразования превышает 8 МиБ». Исходный JPEG — **2 970 896 байт**, 2000×1800 (3,6 млн пикселей); после обязательного преобразования JPEG → PNG — **10 505 277 байт**, больше лимита 8 МиБ. Это стадия валидации/перекодирования, **до storage.put и транзакции**. ServiceDocument = 0, blobs = 0, UPLOAD-история = 0. Последующего GET успешной загрузки нет. Основная БД не изменилась.

Таким образом, для воспроизведения установлена конкретная причина: безопасное преобразование всегда делало PNG из JPEG, резко увеличивало размер и отклоняло допустимый по входному размеру JPEG. Ни имя, ни 409, ни успешный ответ, ошибочно разобранный клиентом, ни последующий GET в этом воспроизведении причиной не были. 100% означает окончание передачи байтов, после которого сервер ещё может отказать. Старые UPLOAD/REMOVE_FILE в истории относятся к отдельным подтверждённым операциям.

Исходного `pexels-kienvirak-4826377.jpg` в проекте нет: использован настоящий валидный JPEG, закодированный Sharp из тестового растра сопоставимого размера, не подложный заголовок/дополнение файла до размера. Поэтому точная причина **отказа именно пользовательского файла** без его байтов и ответа того запроса остаётся неподтверждённой. Найденный и воспроизведённый дефект исправлен; для другого отказа теперь предусмотрена безопасная диагностика.

## Обычные PDF со ссылками и простой интерфейс — 17 ноября 2026

### Причина прежнего отказа и новая классификация

В [validate-service-pdf.mjs](../scripts/validate-service-pdf.mjs) общий список запрещал PDFName `/A` и `/URI` без учёта контекста. Поэтому стандартная аннотация `Link` с действием `A → S: URI` отклонялась даже при обычном HTTPS. Предыдущие описания запрета всех ссылок выше относятся к прежней версии; текущие правила следующие.

Разрешены:

- Абсолютные HTTP/HTTPS URI-действия, в том числе PDFString/PDFHexString, URL с обычными/закодированными пробелами в пути; относительная ссылка — только с проверенным HTTP/HTTPS Base в каталоге PDF.
- Внутренние GoTo по явному массиву назначения (XYZ/Fit/FitH/FitV/FitR/FitB/FitBH/FitBV), строковому или именованному назначению; Named-переходы NextPage/PrevPage/FirstPage/LastPage.
- Оглавление, закладки/Outlines, Dests, обычные Link/Text/Highlight-аннотации, атрибуты размеченного PDF, использующие `/A` не как действие.
- Начальный вид документа через OpenAction-массив внутреннего назначения либо одиночное GoTo без цепочки. Автоматическое открытие внешней ссылки не разрешается.

Действие проверяется как словарь: тип, допустимые поля, схема URI и каждое действие Next (в том числе косвенные ссылки/массивы). Циклы отклоняются, глубина/количество проверок ограничены. Для URI допустимы только HTTP/HTTPS без учётных данных, управляющих символов и обратных слешей. URI других схем (включая javascript/data/file и неподдерживаемые mailto/tel), неизвестные типы действий, Launch, JavaScript, GoToR/GoToE, отправка/импорт форм, опасные Next и автоматические внешние действия отклоняются. Общие запреты AA, скриптов, встроенных файлов/вложений, XFA/AcroForm, мультимедиа, внешних потоков и неподдерживаемых кодеков сохранены. Это намеренно ограниченное подмножество PDF, а не обещание приёма любого документа.

При классификации учитывались определения URI/GoTo/Named в [ISO 32000-1:2008, раздел 12.6](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf). Сервер не выполняет PDF и не переходит по ссылкам. PDF скачивается прежним авторизованным attachment с private/no-store, nosniff и CSP sandbox, без встроенного просмотра. Лимит 20 МиБ, версия PDF 1.0–1.7, проверки структуры/объектов/страниц/потоков, 8 секунд/128 МиБ на процесс, границы декомпрессии и параллелизма не отменены. Антивирусной проверки по-прежнему нет: структурная проверка не гарантирует отсутствие вредоносного содержимого или уязвимостей внешнего PDF-просмотрщика.

Исходный HONOR MagicBook Pro 14 в проекте не найден. Проверены настоящие сформированные pdf-lib документы с URI-аннотациями, HTTP/HTTPS, оглавлением/закладками, внутренними переходами и безвредными аннотациями; именно исходное руководство не проверялось.

### Интерфейс и ошибки

В постоянном описании блока документов оставлено ровно **«Поддерживаемые форматы: JPG, JPEG, PNG, PDF»**. Из предварительного описания услуги также убраны технические размеры. Размеры уже прикреплённых файлов остаются рядом с именами. Автоподготовка больших PNG/JPEG, настоящий прогресс и исчезновение индикатора после успеха сохранены.

Превышение размера отображается непосредственно в строке загрузки с форматом, его актуальным лимитом и предложением выбрать другой файл: PDF — 20 МиБ, передаваемые PNG/JPEG — 8 МиБ. До подготовки изображений остаётся клиентский предел 32 МиБ. Ошибка подготовки не отправляет файл и не имитирует успех. При неудачном чтении списка после подтверждённого UPLOAD сохраняется сообщение об уже записанном документе без требования повторной загрузки.

Техническая diagnostic не приписывается к Error.message и не показывается студенту: она сохранена отдельным полем ServiceApiError, в JSON API и в прежнем безопасном журнале при SERVICES_UPLOAD_DIAGNOSTICS=1. XHR-сеть/отмена/тайм-аут показывают короткие сообщения; в диагностике остаётся стадия и код. Содержимое документов, имена/пути, параметры, учётные данные и персональные сведения в diagnostic не записываются.

Затронуты [валидатор](../scripts/validate-service-pdf.mjs), [тексты хранилища](../src/lib/services-storage.ts), [ошибки API при превышении тела](../src/app/api/services/route.ts), [клиент API](../src/lib/services-ui.ts), [экран заявления](../src/components/services-request-screen.tsx), [описание услуги](../src/components/services-workspace.tsx), [PDF-фикстуры](../scripts/service-pdf-fixtures.mjs), [серверные тесты](../scripts/verify-services.mjs), [UI-тесты](../scripts/verify-services-ui.mjs) и эта документация.
