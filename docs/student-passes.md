# Электронные студенческие пропуска

## Подготовка и полномочия

1. Остановите процессы, которые пишут в рабочую SQLite, и выполните `npm run db:passes`. Команда делает согласованную копию через SQLite `VACUUM INTO`, проверяет миграцию и повторный запуск на отдельной копии, сверяет прежние записи и проверяет целостность. После успешной проверки команда применяет миграции к исходной БД. Для пробного прогона используйте `node --env-file-if-exists=.env scripts/prepare-clearance.mjs --passes`. Ограничьте доступ к каталогу `.local`, где хранятся резервные копии.
2. Перед первой выдачей задайте постоянный случайный `PASS_TOKEN_KEY` (минимум 32 символа) в серверном окружении. При отсутствии отдельного ключа используется `BETTER_AUTH_SECRET`. Один и тот же ключ нужен всем экземплярам приложения и при восстановлении из резервной копии. Замена ключа влияет на отображение ранее выданных QR. Для их восстановления верните прежний ключ либо оформите новую выдачу. Проверка ранее предъявленного QR использует сохранённый хеш.
3. Доверенный оператор сервера назначает существующему аккаунту `ADMIN` или `TECHNICAL_STAFF` права командой `npm run passes:grant -- <email> verify|manage|both|none`. Укажите один режим. `verify` разрешает только проверку QR, `manage` разрешает выдачу, перевыпуск, отзыв и просмотр истории, `both` включает оба права, `none` отзывает назначение. Назначение привязано к роли на момент выдачи и проверяется с текущей ролью и сессией при каждом запросе.

Студент открывает только свой пропуск. Преподаватель и сотрудник деканата работают в своих кабинетах. Назначения службы, деканата и рассмотрения услуг сами по себе прав на пропуска не дают.

## Выдача и перевыпуск

- Войдите с полномочием `manage`, откройте «Электронные пропуска» в кабинете администратора или технического сотрудника. Найдите существующего студента по университетской почте и нажмите «Выдать пропуск». После выдачи студент увидит QR в профиле и в окне «Пропуск» на главной. Если у аккаунта ещё нет записи студенческого профиля, при выдаче создаётся пустая запись в существующей модели. ФИО отображается из учётной записи до заполнения официальных полей.
- Для замены студент подаёт существующее заявление «Перевыпуск пропуска». Сотрудник с полномочиями на услугу проводит его через рассмотрение до статуса «Исполнено». Затем оператор пропусков выбирает исполненное заявление этого студента, указывает причину и нажимает «Перевыпустить пропуск». Операция заменяет действующий QR и связывает новый пропуск с заявлением. Одно заявление используется однократно. Фотография берётся из актуального официального профиля. Приложение к заявлению проверяется по обычному процессу услуги.
- Для отзыва укажите причину и нажмите «Отозвать пропуск». История показывает дату выдачи, оператора, статус, причину и дату закрытия, а для замены также заявление. Новая выдача после отзыва выполняется вручную.

## Проверка

Сотрудник с полномочием `verify` открывает раздел «Электронные пропуска». На телефоне можно сделать снимок из поля «Снимок QR-кода». На компьютере можно выбрать снимок или считать код внешним сканером в поле «Код со сканера». Снимок декодируется в браузере. Сотрудник увидит один из четырёх результатов. Для действующего пропуска доступны ФИО, группа и официальная фотография для сверки с предъявителем.

Статический QR можно сфотографировать или скопировать. Допустимы повторные считывания в пределах 30 проверок в минуту на сотрудника. Каждая проверка читает актуальный статус. По QR невозможно удостоверить физическое присутствие владельца. Для этого нужна визуальная сверка с официальной фотографией. СКУД и турникеты находятся вне этой системы.

## Хранение и транспорт

База хранит случайный 256-битный идентификатор записи и хеш токена. Сервер воспроизводит токен через HMAC с постоянным серверным ключом. QR содержит только непрозрачную строку с версией формата. Студенческая карточка получает готовое изображение в ответе с запретом кеширования. Проверка передаёт строку в теле защищённого POST. На прокси и в инструментах диагностики исключите журналирование тел запросов и ответов этого API. Используйте HTTPS в production.

Уникальный индекс по студенту и активному слоту защищает от двойной выдачи. Даты, причины, операторы и связь с существующим заявлением хранятся в истории пропусков. Проверка версии записи и закрытие старого пропуска с созданием нового выполняются в транзакции. Бизнес-операции используют Prisma. При переходе на PostgreSQL перенесите ограничения из SQLite-миграции, включая проверку активного слота и семантику уникального индекса с NULL.

## Демонстрация и регрессия

После `npm run build` запустите `npm run test:passes`. Для прогона на изолированном dev-сервере используйте `npm run test:passes -- --development`. Тест готовит изолированную SQLite-базу, выдаёт образцы через браузер, декодирует QR с экрана и проверяет выдачу, отзыв, перевыпуск, полномочия и размеры интерфейса. Известные демоаккаунты помечаются «Образец» автоматически. Для среды, целиком заполненной синтетическими данными, задайте `PASS_SAMPLE_MODE=true`.
