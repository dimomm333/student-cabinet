# Кабинет сотрудника деканата

14 ноября 2026. `DEANERY_STAFF` — самостоятельная пятая роль с домашним маршрутом `/deanery`. Она не наследует права ADMIN или TECHNICAL_STAFF. Общие [roles.ts](../src/lib/roles.ts), [access.ts](../src/lib/access.ts) и оболочка кабинетов обеспечивают вход, выбор кабинета, серверную проверку роли и адаптивное меню.

Следующий реализованный этап: [редактор регулярного расписания и разовых изменений](./schedule-editor.md). Он заменяет описанный ниже первоначальный просмотр на `/deanery/schedule` и заполняет пустые демосвязи по явной карте фикстур. Исторические ограничения первого этапа ниже следует читать с учётом этого расширения.

## Область доступа

Используется существующий `AcademicDepartment`, а не новая модель института. `DeaneryStaffProfile` содержит должность, `DeaneryDepartmentAssignment` явно связывает сотрудника с одним или несколькими подразделениями. Для работы со всем институтом нужно явно назначить каждое его подразделение; совпадение текстового `faculty` не предоставляет полномочий.

Студент доступен только через `StudentProfile.group.departmentId`, соответствующий живому назначению сотрудника. Название группы, текстовое поле `institute`, родительская группа и параметры клиента не определяют права. Студенты и группы без явного подразделения недоступны. Назначение родительской группы не даёт доступ к подгруппе другого подразделения.

[deanery-repository.ts](../src/lib/deanery-repository.ts) предоставляет `getDeaneryContext`, `deaneryGroupWhere`, `deaneryStudentWhere`, `requireDeaneryGroup` и `requireDeaneryStudent`. Сервисные функции проверяют текущую роль из БД и добавляют область как обязательный AND к каждому чтению. Предикаты содержат живую связь назначения и текущую роль пользователя, чтобы отозванное назначение не оставалось действующим в сохранённом объекте области. Пустая область не означает «все подразделения».

[withDeanery](../src/lib/deanery.ts) получает исполнителя исключительно через `requireRole("DEANERY_STAFF")`. ID исполнителя нельзя передавать из URL. Репозиторий не принимает произвольный Prisma where от клиента. Неизвестный и недоступный ID получают одинаковое состояние 404. Новые журналы и заявки должны использовать этот вход и добавлять предикаты области непосредственно к операциям. Наличие проверки области само по себе не разрешает будущие изменения данных: полномочия на запись нужно проектировать отдельно.

Сессии, токены и область полномочий не помещаются в общий кеш. Сохранены `connection()`, Cache Components и Suspense/loading. SEC-01, SEC-02 и SEC-03 и allowlist auth API не изменены. ADMIN также не получает доступ к кабинету деканата автоматически.

## Работающие страницы

| Маршрут | Возможности |
| --- | --- |
| `/deanery` | Назначенные подразделения и реальные количества студентов и групп своей области |
| `/deanery/students` | Просмотр ФИО, почты, группы, курса, номера студенческого билета; до 200 записей с честным сообщением об ограничении |
| `/deanery/groups` | Код группы, программа, курс, подразделение, число студентов; до 200 записей |
| `/deanery/schedule` | Выбор своей публичной группы и недели, просмотр опубликованных занятий через существующий общий репозиторий расписания и общий ScheduleView; каталог ограничен 500 публичными группами |
| `/deanery/profile` | Общий профиль: ФИО, рабочая почта, роль, назначенные подразделения, должность, дата регистрации, статус подтверждения почты |

Фильтры `departmentId`, `groupId`, `studentId` ограничивают выдачу, но не расширяют область. Они поддерживаются сервером на страницах списков; интерфейс расширенного поиска и пагинации пока не реализован. Отдельные страницы чужих профилей и API доступа к студентам не создавались. В списки не попадают пароли, сессии или служебные данные авторизации.

Расписание доступно только для чтения и только в пределах существующей границы публикации. Скрытые занятия, приватные преподаватели и приватные группы не открываются новой ролью. Общие занятия могут относиться к нескольким подразделениям, но из карточки убираются названия групп вне назначенной области. Публичный API не меняется; в него не добавляются профили или назначения деканата.

`/deanery/grades`, `/deanery/requests`, `/deanery/notifications` — честные страницы «В разработке». Электронный журнал, оценки, исправление личных данных, обработка заявлений, уведомления, QR-пропуска и управление расписанием не реализованы. Изменение роли, назначений, пользователей и инфраструктуры через кабинет/API недоступно. Все профили остаются только для чтения.

## Консультации

В разделе «Консультации» (`/deanery/consultations`) откройте форму «Новая консультация». Выберите преподавателя, дисциплину, дату, начало и окончание по московскому времени, корпус, аудиторию и группы. Для каждой выбранной группы нужна связь преподавателя и дисциплины через учебное назначение или расписание пар. Система проверяет занятость преподавателя и аудитории при добавлении и редактировании. Для изменения или отмены используйте действия на карточке. Сотруднику требуется явное назначение на подразделения всех указанных групп. [Правила и развёртывание](./consultations.md)

## Миграция и демонстрационная запись

[Миграция](../prisma/migrations/20261114100000_deanery_staff/migration.sql) добавляет две таблицы с внешними ключами и составным уникальным ключом назначения. Старые таблицы не пересоздаются и не очищаются. В SQLite Role хранится как TEXT, поэтому расширение Prisma enum не требует изменения существующих User. При переходе на PostgreSQL потребуется нативная миграция enum и PostgreSQL-вариант DDL; прикладные проверки используют переносимый Prisma API.

`npm run db:deanery` сначала создаёт согласованный SQLite-снимок через VACUUM INTO в игнорируемом локальном каталоге, проверяет миграцию и двукратный seed на копии, сверяет все прежние строки, а затем применяет миграцию и добавляет только демоаккаунт деканата. Перед применением проверяется, что исходная БД не изменилась после снимка. Для развёртывания выполняйте команду при остановленных операциях записи. Скрипт специфичен для SQLite; для PostgreSQL нужен согласованный pg_dump/backup и штатный migrate deploy.

Демоаккаунт: `olga.kuznetsova@example.test`, переменная `DEMO_DEANERY_PASSWORD`. Пароль задаётся через окружение либо безопасно генерируется существующим seed и сохраняется только в игнорируемом `.env.demo.local`. Пароль не публикуется. Предыдущие пароли, аккаунты и сессии не меняются. Seed идемпотентен и не восстанавливает отозванные назначения существующего профиля.

При первой инициализации демопрофилю явно назначается подразделение «Учебная кафедра» института цифровых технологий (существующее при совпадении уникальной пары или вновь созданное). Уже существующие группы не перепривязываются автоматически: это изменило бы область доступа без решения ответственного сотрудника. Если группы не связаны с назначенным подразделением, демопанель честно показывает нулевые количества. До следующего этапа необходимо проверить реальные связи групп с подразделениями и выполнить назначения доверенной административной процедурой вне публичного приложения.

## Проверки

Наборы выполняются на отдельных SQLite-копиях с временными паролями. Тесты проверяют сохранность исходной БД. Команды:

1. `npm run typecheck`
2. `npm run lint`
3. `npm run build`
4. `npm run test:auth`
5. `npm run test:auth:navigation`
6. `npm run test:auth:navigation -- --production`
7. `npm test` и `npm run test:schedule:browser`
8. `npm run test:api`
9. `npm run test:deanery`

Все перечисленные команды успешно выполнены 14 ноября 2026 года в указанном порядке. Навигация dev/production: 0 предупреждений Next.js и 0 ошибок браузера, включая Blocking Route/Instant. Дополнительно `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code` подтвердил отсутствие расхождений между основной БД и схемой. Перед миграцией и после неё проверены прежние строки, внешние ключи и `integrity_check`; двукратный seed не изменил результат.

Последний набор проверяет несколько назначений, чужие ID и подразделения, отсутствие привязок, текстовые совпадения, межкафедральную иерархию групп, живой отзыв назначения/роли, отсутствие автоматических прав ADMIN, изоляцию расписания, вход через форму, desktop/mobile и неизменность исходной БД. Общие тесты авторизации и навигации охватывают все пять ролей и шесть демонстрационных аккаунтов. Проверки API и запрос API с сессией деканата подтвердили отсутствие персональных полей. Результаты сохранены в игнорируемых JSON-файлах тестов. Mobile проверен в браузерной эмуляции 390 px; физические устройства и production Linux VPS не проверялись.
