## SEC-01: два независимых ограничения входа

[login-throttle.ts](../src/lib/login-throttle.ts) использует существующую таблицу RateLimit. Новые таблицы и миграции не нужны.

- Идентификатор приводится к `trim().toLowerCase()`. По нему вычисляется HMAC-SHA256 с серверным секретом; email в ключе RateLimit не хранится.
- На каждый идентификатор разрешено пять попыток за фиксированное окно 60 секунд. Атомарный параметризованный SQLite `INSERT ... ON CONFLICT ... RETURNING` резервирует попытку до проверки пароля, в том числе между параллельными процессами.
- Счётчик одинаково создаётся для существующих и неизвестных email, без обращения к User. Ответ блокировки имеет общий код/сообщение; `Retry-After` зависит от окна, а не существования аккаунта.
- Отказанные запросы не сдвигают начало окна. Постоянной блокировки, изменения User и накопительного увеличения срока нет. Успешный вход очищает только своё окно; конкурентный успех не очищает следующее окно.
- Посторонний Origin отклоняется до расходования квоты. Ошибка хранилища приводит к 503, не к обходу ограничения.
- Старые счётчики account удаляются периодически. Дополнительный лимит Better Auth — 60 запросов signin в минуту на проверенный IP либо общую корзину прямого локального запуска. Он защищает ресурс; основной независимый лимит остаётся по идентификатору.

Квота аккаунта применяется в поддерживаемом before hook Better Auth, после HTTP IP-лимитера и до проверки пароля. Запрос, уже отвергнутый IP-лимитером, не создаёт новую строку account в RateLimit. Это отдельно проверено без большого числа запросов: счётчик IP доведён до порога напрямую только в тестовой базе. After hook очищает квоту при подтверждённом успешном входе.

[auth-transport.ts](../src/lib/auth-transport.ts) удаляет присланные X-Forwarded-For, Forwarded, X-Real-IP, CF-Connecting-IP, True-Client-IP и внутренние IP-заголовки. В прямом режиме они не могут менять корзину или IP сессии. Web Request не предоставляет надёжный socket peer address, поэтому адрес клиента из таких заголовков не угадывается. Прямой режим допускается только для loopback baseURL.

В proxy-режиме приложение принимает один валидный IP только из X-LKS-Client-IP и только при верном X-LKS-Proxy-Key. Ключ сравнивается через digest и timingSafeEqual. Затем proxy-ключ удаляется из запроса, передаваемого Better Auth; проверенный IP передаётся через внутренний заголовок. Отсутствующий ключ, неверный ключ или цепочка адресов вместо одного IP дают 403.

**Остаточный риск DoS:** любой парольный limiter по аккаунту может временно препятствовать входу владельца, если атакующий знает email. Здесь окно ограничено 60 секундами и не продлевается отказанными запросами, аккаунт не выключается, успешный вход сбрасывает счётчик. Продолжающий атаку противник может снова занять следующее окно. Полная защита от распределённой атаки требует мер на границе сети, мониторинга и, при необходимости, отдельного проектирования challenge/MFA. Они не имитируются в текущем этапе. Жёсткого обещания «account DoS невозможен» нет.

## Reverse proxy и firewall

Для внешнего адреса конфигурация должна содержать:

```dotenv
BETTER_AUTH_URL=https://lks.example.edu
AUTH_TRUST_PROXY=true
# AUTH_PROXY_SECRET задаётся отдельно через хранилище секретов.
```

AUTH_PROXY_SECRET должен быть отдельным случайным значением не менее 32 символов, известным только proxy и приложению. Не используйте для него пароль аккаунта и не помещайте значение в Git, JavaScript клиента, URL или access log. Пример окружения находится в [.env.example](../.env.example).

Backend следует запускать на loopback:

```bash
npm run start -- --hostname 127.0.0.1
```

Порт Node.js должен быть закрыт firewall от прямых внешних подключений. Если proxy расположен на другом узле, разрешайте только его адрес/подсеть и защищённое соединение между узлами. Проверка proxy-ключа дополняет firewall, а не заменяет его.

Пример части Nginx-конфигурации после настройки TLS:

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header X-LKS-Client-IP $remote_addr;
    proxy_set_header X-LKS-Verified-IP "";
    proxy_set_header X-Forwarded-For "";
    proxy_set_header X-Real-IP "";
    proxy_set_header Forwarded "";

    # Файл вне репозитория, доступен только администраторам proxy.
    # Он содержит proxy_set_header X-LKS-Proxy-Key со значением из secret store.
    include /etc/nginx/private/lks-proxy-key.conf;
}
```

Proxy должен **заменять**, а не добавлять к клиентскому значению X-LKS-Client-IP и X-LKS-Proxy-Key. Если перед Nginx есть CDN/LB, настройка real_ip должна доверять только его реальным адресам; нельзя доверять произвольным цепочкам XFF или всему интернету. Выбранный origin должен точно совпадать с BETTER_AUTH_URL. Публичные HTTP-запросы следует перенаправлять на HTTPS на proxy; атрибут Secure приложения включается по HTTPS baseURL.

Тесты проверили отказ при неверном ключе, использование правильного IP и игнорирование XFF/внутреннего заголовка. Проверена выдача Secure/HttpOnly/SameSite=Lax при HTTPS-конфигурации. Настоящий TLS-транспорт, сертификаты, firewall и конкретный внешний Nginx не тестировались.

## SEC-02: абсолютные восемь часов

[session-policy.ts](../src/lib/session-policy.ts) задаёт единый предел от первоначального createdAt. [auth.ts](../src/lib/auth.ts) использует поддерживаемые Better Auth database/API hooks:

1. `session.create.before` назначает серверное createdAt и ограничивает expiresAt восемью часами, включая rememberMe=false, для которого библиотека раньше выбирала 24 часа.
2. `session.update.before` не разрешает изменить исходное createdAt и ограничивает изменение expiresAt исходным абсолютным пределом. Без надёжного идентификатора исходной сессии продление отклоняется. Автопродление по-прежнему отключено.
3. After hook get-session проверяет срок на каждом чтении, включая прямые серверные вызовы auth.api.getSession. Старые записи за восемью часами возвращают null, даже если expiresAt находится в будущем. Ещё действующие длинные записи сокращаются до предела.
4. [access.ts](../src/lib/access.ts) дополнительно проверяет абсолютный срок перед чтением пользователя/роли.

Для предварительного сокращения всех старых строк, без изменения User, Account, News и профилей:

```bash
npm run auth:harden-sessions
```

[harden-sessions.mjs](../scripts/harden-sessions.mjs) выполняет условные обновления только Session, сохраняет более короткие сроки и безопасен при повторном запуске. Проверка чтения работает сразу после обновления кода, даже если команда ещё не запускалась. Старые сессии не сохраняют право работать сверх восьми часов. При развёртывании сначала остановите старую версию приложения, примените новую сборку/maintenance-команду и запустите новую версию.

В тестах возраст моделируется только изменением тестовых Session: время ОС не меняется, восемь часов в реальном времени не ожидаются. Продление expiresAt и обновление updatedAt не позволяют обойти предел createdAt+8h.

## SEC-03: подтверждение выхода

After hook sign-out в [auth.ts](../src/lib/auth.ts) проверяет подписанный входной cookie через API Better Auth и затем отсутствие соответствующей Session. Проверка выполняется после штатной попытки удаления библиотеки.

Если строка осталась или прочитать состояние невозможно, hook возвращает **503 / SIGN_OUT_UNCONFIRMED** и удаляет подготовленные заголовки истечения cookie. Интерфейс показывает существующее сообщение об ошибке и позволяет повторить запрос. Пользователь не получает ложного подтверждения выхода. После подтверждённого удаления cookie очищается штатно, повтор старого cookie не авторизует.

При реальном отказе хранилища старая сессия может оставаться действительной до успешного отзыва либо истечения срока. Исправление обеспечивает достоверность результата и повтор, а не обещает удаление из недоступной базы. Сервер пишет обезличенное событие auth.sign_out_revocation_unconfirmed, без токена или тела запроса. Для production необходимо подключить оповещение по этому событию.

Использованы поддерживаемые [hooks Better Auth](https://better-auth.com/docs/concepts/hooks) и Prisma. Файлы node_modules не редактировались.

## DEP-01: минимальное изменение зависимости

На дату работы последняя typescript-eslint — 8.72.2, версии 8.72.3 нет, а в minimatch 10 нет релиза после 10.2.6. [Advisory](https://github.com/advisories/GHSA-g3hv-75wg-m249) указывает исправление начиная с 11.0.1.

В [package.json](../package.json) добавлен узкий npm override `@typescript-eslint/typescript-estree → minimatch: 11.0.1`. Изменились один пакет и одна новая транзитивная зависимость. Остальные потребители minimatch 3.1.5 не затронуты; Next.js, Prisma, Better Auth и typescript-eslint не обновлялись.

Это выход за upstream-диапазон minimatch 10 именно у данного потребителя, поэтому совместимость проверена отдельно: CommonJS require из контекста typescript-estree, четыре характерных glob-сценария, ESLint, TypeScript и production build. Текущий потребитель использует поддерживаемый интерфейс minimatch(file, pattern, { dot: true }). Override закреплён точно и должен быть пересмотрен при будущем обновлении ESLint/Next config, чтобы не удерживать устаревшую версию. `npm audit fix --force` не использовался.

## Повторное тестирование

[verify-auth-security.mjs](../scripts/verify-auth-security.mjs) создаёт новый файл SQLite через VACUUM INTO, меняет пароли только в копии на случайные временные и запускает сервер на 127.0.0.1. Перед destructive-операциями проверяется, что URL базы указывает на отдельный локальный каталог. Trigger отказа DELETE и моделирование срока никогда не применяются к основной базе. Тест сравнивает исходные User, Account, News и профили до и после через fingerprint.

```bash
npm run typecheck
npm run lint
npm run build
npm run test:auth
npm run test:auth:dev
npm audit
npm audit --omit=dev
```

Уже запущенный сервер для тестов не требуется. Production-набор использует собранную версию; dev-набор запускает настоящий next dev на копии проекта. В Windows дочернее дерево процессов останавливается по PID, созданному самим тестом. Тесты не выполняются против внешних серверов.
