# Постоянные инструкции проекта ЛКС

Эти правила действуют для всех будущих задач Codex в этом репозитории.

## 1. Совместимость с Linux

- Разработка ведётся на Windows 11, production будет работать на Linux VPS.
- Не используй абсолютные Windows-пути в коде и переносимых конфигурациях. Формируй файловые пути средствами Node.js относительно проекта или явно заданного окружения.
- Учитывай регистр имён файлов и каталогов: пути импортов должны точно совпадать с именами на диске.
- Не используй платформозависимые системные команды в логике приложения. Переносимые npm-скрипты не должны зависеть от PowerShell, cmd.exe или Windows-утилит.
- Обеспечивай совместимость Prisma, Next.js, npm-скриптов и зависимостей с Linux. Сохраняй воспроизводимую установку через lock-файл; не переноси Windows-сборки и node_modules на Linux вместо установки и сборки на целевой платформе.
- Конфигурацию сервера и БД храни в переменных окружения. В примерах окружения допускаются только безопасные значения без секретов.

## 2. Архитектура и данные

- Перед изменениями изучай существующую архитектуру, Prisma-схему, серверный слой, связанные компоненты и документацию.
- Используй существующую Prisma-схему и общую серверную бизнес-логику.
- Не дублируй данные, таблицы и реализацию функций для разных кабинетов. Переиспользуй общие серверные функции и интерфейсные компоненты.
- Сохраняй возможность будущего перехода с SQLite на PostgreSQL: предпочитай Prisma API, изолируй необходимый СУБД-зависимый SQL и явно описывай ограничения переносимости.
- Не пересоздавай проект и не удаляй существующие данные. Изменения схемы выполняй сохраняющими данные миграциями; перед применением к существующей БД обеспечивай согласованную резервную копию и проверку сохранности данных.

## 3. Безопасность

- Все проверки прав выполняй на сервере, близко к чтению или изменению данных. Проверка layout и скрытые пункты меню не заменяют авторизацию страниц, Route Handlers и Server Actions.
- Не ослабляй защиту авторизации и сессий. Сохраняй SEC-01, SEC-02 и SEC-03: ограничения входа, абсолютный срок сессии без продления и подтверждённый выход.
- Не публикуй и не включай в Git секреты, пароли, токены, рабочую базу данных, её резервные копии и журналы с чувствительными данными.
- При добавлении функций проверяй доступы всех четырёх ролей: STUDENT, TEACHER, ADMIN и TECHNICAL_STAFF. Проверяй анонимный доступ и попытки получить чужие данные подменой параметров.
- Не помещай сессии, токены и решения о правах доступа в общий кеш. Сохраняй динамическую проверку сессий и корректные границы Suspense/loading при работе с Cache Components.
- При изменении защищённых кабинетов учитывай [решение для Better Auth и Cache Components](./docs/cache-components-auth.md). Не отключай Cache Components глобально и не скрывай предупреждения настройками диагностики вместо исправления причины.

## 4. Проверки

- После изменений запускай подходящие автоматические тесты. Для нового поведения и исправлений ошибок добавляй необходимые регрессионные проверки.
- Перед завершением выполняй TypeScript, ESLint и production build: `npm run typecheck`, `npm run lint`, `npm run build`. Команды с общей генерацией Prisma Client и артефактов Next.js выполняй последовательно, чтобы избежать гонок записи.
- При изменении авторизации или защищённых страниц запускай тесты безопасности и навигации: `npm run test:auth`, `npm run test:auth:navigation` в next dev и `npm run test:auth:navigation -- --production` после production build.
- Проверяй прямое открытие страниц, переходы через меню, возврат на главную кабинета, выход, смену ролей и отказ доступа к чужим кабинетам. Проверяй отсутствие предупреждений Blocking Route и Instant в браузере.
- Используй изолированные тестовые базы и временные учётные данные. Тесты не должны изменять основную БД, её пароли и сессии.
- Не сообщай об успешном тесте, если он реально не выполнялся. Явно указывай невыполненные, упавшие или заблокированные проверки и причины.

## 5. Порядок работы

- Продолжай существующую реализацию; не заменяй её новой без необходимости и задания.
- Сохраняй изменения пользователя и ранее выполненную работу. Не откатывай несвязанные изменения.
- Не устанавливай ненужные библиотеки. Сначала проверяй возможности существующих зависимостей и компонентов.
- Не переходи к другим этапам, модулям или функциям без задания.
- В конце сообщай, что изменено, какие файлы затронуты, что фактически проверено и какие ограничения остались.
